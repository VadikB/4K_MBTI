# Совместная разработка

Командный контракт Enterprise Vibe Coding находится в `AGENTS.md`. Для
нетривиальной задачи используйте `docs/evc/task-template.md`, а перед передачей
Pull Request — `docs/evc/review-checklist.md`. Критерии фиксации неизменяемого
baseline описаны в `docs/evc/baseline-v1.md`.

## Основной процесс

### Текущий этап подготовки EVC baseline

По решению владельца проекта от 2026-09-29 WEEEK пока не используется.
До его подключения основанием изменения служит локальная задача в
`docs/evc/tasks/` с результатом, границами, проверками и откатом. В PR указывается
путь к этой задаче; номер WK не требуется и не придумывается. Для веток этого
этапа используется `codex/<short-name>`, для коммитов — краткое описание изменения
(при наличии — локальный ID, например ART-01).

Остальные правила PR, CI и продвижения между контурами сохраняются. Подготовка
к baseline не означает его утверждение: требования и доказательства для точного
коммита/тега перечислены в `docs/evc/baseline-v1.md`.
Ниже описан процесс с WEEEK после его подключения.

`main` — единственная постоянная интеграционная ветка. Она должна оставаться
готовой к развёртыванию на тестовом контуре.

Независимые пакеты готовятся параллельно, а изменение `main` и выпуск выполняются
последовательно. Обычно одновременно активны 2–4 пакета. Для каждого пакета нужны
отдельные задача, ветка, worktree и PR; увеличение лимита требует явного обоснования
стоимости синхронизации.

Каждая задача WEEEK выполняется в отдельной короткоживущей ветке:

- `feature/WK-123-short-name` — новая функциональность;
- `fix/WK-123-short-name` — исправление;
- `hotfix/WK-123-short-name` — срочное исправление pilot.

Прямые push в `main` не используются. Изменения попадают туда только через
Pull Request после обязательного CI.

Рабочий шаг и выпуск кандидата — разные единицы процесса. Один целостный,
независимо принимаемый результат может включать несколько зависимых карточек и
рабочих коммитов в одной ветке; отдельный PR для каждой карточки не требуется.
Рабочий шаг завершается адресными проверками, коммитом и обновлением `STATE.md`.
Полный применимый набор выполняется для точного SHA кандидата перед передачей в
review; его не нужно повторять после каждого промежуточного коммита, пока не
изменилось проверенное основание и не обнаружена ошибка.

## Начало работы

```bash
git switch main
git pull --ff-only
git worktree add ../Agent4K-WK-123 -b feature/WK-123-short-name main
cd ../Agent4K-WK-123
```

Для текущего этапа без WEEEK используется ветка `codex/<short-name>`. Один worktree
не используется несколькими пакетами и не создаётся внутри отслеживаемого каталога.

Один раз после клонирования включите локальную проверку коммитов:

```bash
./scripts/setup_git_hooks.sh
```

## Перед Pull Request

Используйте [рабочий цикл агента](docs/evc/agent-workflow.md) и
[матрицу проверок](docs/evc/verification-matrix.md). До создания PR выполните
локальный минимум для типа изменения и заполните отчёт. Для docs это diff,
ссылки и согласованность; backend/JS/БД требуют соответствующих тестов матрицы.
Если обязательная локальная проверка заблокирована, готовность не заявляется;
исключение для диагностического draft PR описано в рабочем цикле.

Полный действующий GitHub CI (`frontend`, `pytest`) обязателен перед слиянием,
в том числе для docs. Integration выполняется только на отдельной изолированной
БД с `test`/`pytest` в имени; пропуск из-за отсутствия БД не равен успеху.

В PR обязательны локальная задача (пока WEEEK не используется) или WEEEK после
подключения, результаты проверок, причины пропусков, риски и откат.

На текущем этапе ручное review и approval не являются обязательным gate приёмки PR.
Автор выполняет self-review по `docs/evc/review-checklist.md`; приёмка PR опирается на
выполненные критерии задачи, обязательные CI jobs, разрешённые зависимости/пересечения
и актуальность относительно `main`. Это временное процессное решение действует до
отдельного решения владельца о возврате обязательного ручного review. Оно не отменяет
человеческие решения по стоп-условиям, допуск выпуска, стендовую/предметную приёмку
или требования baseline.

Каждая задача и PR явно содержат:

- `depends_on`: номера PR/задач либо `[]`; зависимый PR не входит в merge queue раньше
  зависимостей;
- класс изменённых путей (`low`, `medium`, `high`) и выбранные по
  [матрице](docs/evc/verification-matrix.md) локальные проверки;
- известные пересечения файлов с открытыми PR и порядок их разрешения.

CI автоматически публикует в job summary класс риска и пересечения файлов с другими
открытыми PR. Это ранний сигнал координации, а не разрешение конфликта и не замена
`depends_on`, self-review или повторной проверки объединённого состояния.

Быстрый CI автоматически запускается при открытии, повторном открытии, после
нового commit и при переходе из draft в `Ready for review`. В draft выполняются
jobs `frontend` и `pytest`, но шаг `Verify application release` явно отложен.
Полный CI с integration и browser впервые запускается при создании PR сразу не в
draft либо при переходе draft PR в `Ready for review`; затем он повторяется после
каждого нового commit, пока PR остаётся Ready. Новый commit в draft не запускает
дорогой набор. Устаревший полный прогон того же PR отменяется при запуске нового.
При переводе в `Ready for review` на неизменённом SHA повторяются быстрые jobs,
включается release-проверка и запускается `full-verification` точного SHA.
Unit и HTTP выполняются только в job `pytest`, не дублируются в полном workflow.
Кандидат без нового согласованного номера нельзя принять в `main`. Ручная метка
для полного прогона не требуется. Push рабочей ветки без PR не запускает CI.
Merge в `main` выполняет только `deploy-test` уже проверенного commit. `skip-ci`
не используется для продвижения кандидата.

## Коммиты и merge

Коммит описывает один логический результат и начинается с номера тикета:

```text
WK-123 Add assessment preparation queue
```

Для merge используется squash merge. Ветка удаляется после merge.

Предпочтительный путь — GitHub merge queue. Если она не включена, перед merge PR
обновляется от текущего `main` без переписывания чужой работы, после чего обязательные
jobs повторно проходят для актуальных head/base. Короткий gate перед squash merge:
зависимости слиты, пересечения разрешены, self-review завершён, required checks зелёные.
Одновременно сливается только один PR; следующий кандидат проверяется уже относительно
нового `main`.

Перед `Ready for review` кандидат готовится единственной командой:

```bash
npm run ready:prepare -- --candidate X.Y.Z
```

Команда обновляет `origin/main` и отклоняет ветку на устаревшей базе. Сначала
обновите ветку из актуального `origin/main`, затем повторите подготовку. Версия
должна быть непосредственным PATCH, MINOR или MAJOR-преемником версии базы;
отдельный повторный bump запрещён. После merge локальный `main` синхронизируется
через `git pull --ff-only`; сам deploy версию не изменяет.

Перед началом действия явно фиксируются независимые флаги:

- `branch_push` — сохранить рабочую ветку в remote;
- `pr` — создать или обновить точку review;
- `merge` / `deploy` — принять результат в `main` и развернуть его на `test`;
- `version_bump` — присвоить номер приложению-кандидату;
- `artifact_publish` — опубликовать предметный артефакт через его lifecycle.

Один флаг не включает остальные. Для обычного рабочего шага по умолчанию:
`merge=false`, `deploy=false`, `version_bump=false`,
`artifact_publish=false`; `branch_push` и `pr` определяются планом передачи.
Публикация предметного пакета не следует автоматически из merge приложения.

Версия приложения не увеличивается на каждый рабочий коммит или draft PR. Каждый новый
выпускаемый набор изменений продукта получает один новый номер `MAJOR.MINOR.PATCH`.
Тип (`major`, `minor`, `patch`) утверждается по продуктовой задаче; `minor` обнуляет
PATCH, `major` обнуляет MINOR и PATCH. Ответственный готовит кандидата один раз:

```bash
npm run bump:version -- patch --dry-run
npm run bump:version -- patch --candidate 2.0.2
npm run build:web
```

Непосредственно перед переводом PR в `Ready for review` выполняется единый
preflight. Для product-изменений без номера команда заранее выводит следующий
кандидат и завершается без изменения файлов; после решения владельца она
идемпотентно назначает номер, пересобирает frontend и проверяет release gate:

```bash
git fetch origin main
npm run ready:prepare
npm run ready:prepare -- --candidate 2.0.48
git diff --check
```

PR переводится в `Ready for review` только после успешного preflight, commit и
push подготовленного кандидата. Для изменений только в `docs/`, `tests/` и CI
номер не назначается. Это не отменяет обязательный CI и отдельное решение владельца
на `version_bump`.

Повтор подготовки того же кандидата, CI или деплоя не поднимает номер. Повторный
деплой того же commit и продвижение test → pilot сохраняют номер. При изменении
состава уже выпущенной сборки нужен новый номер. Перед merge параллельной ветки
сверьте свежий `main`: CI отклоняет неизменённый/несогласованный номер. Переход
`2.1.37 → 2.0.1` — разовое решение REL-VERSION-01, не общее правило понижения.
Непосредственно перед слиянием повторно проверьте актуальный `origin/main` и
обязательные проверки точного head; старый зелёный CI параллельной ветки не
подтверждает уникальность номера после продвижения `main`.

## Контуры

- Локальная среда предназначена только для разработки.
- Каждый merge в `main` автоматически развёртывается на `test`.
- На `pilot` вручную продвигается тот же commit или артефакт, который прошёл
  проверку на `test`.
- Ручная загрузка файлов с компьютера разработчика на сервер запрещена.

У `test` и `pilot` должны быть разные базы данных, `.env`, секреты и внешние
интеграции. Рабочие данные pilot не копируются в test без обезличивания.

Каждый integration job создаёт собственную PostgreSQL-БД с `test`/`pytest` в имени;
общая БД между параллельными jobs запрещена. `concurrency` применяется к deploy/release,
чтобы не менять один контур одновременно, но не отменяет и не дедуплицирует обязательные
проверки пакетов.

## Приёмка

В локальной задаче, а после подключения WEEEK — в тикете, фиксируются:

- ссылка на Pull Request;
- commit и версия тестовой сборки;
- URL тестового контура;
- инструкция проверки;
- результат и имя тестировщика.

Если часть общей тестовой сборки не прошла приёмку, изменение исправляется
новым Pull Request либо откатывается отдельным revert-коммитом.

## Секреты деплоя test

GitHub Environment `test` должен содержать:

- `TEST_SSH_HOST` — адрес сервера;
- `TEST_SSH_USER` — пользователь SSH;
- `TEST_SSH_PRIVATE_KEY` — закрытый ключ CI;

Публичный ED25519 fingerprint сервера зафиксирован в workflow. Перед SSH
подключением runner получает host key, сверяет его fingerprint и оставляет
`StrictHostKeyChecking` включённым. Многострочный secret `TEST_SSH_KNOWN_HOSTS`
не используется.

После успешных frontend и backend jobs workflow подключается к серверу и
запускает `scripts/deploy_test_remote.sh`. Скрипт обновляет только test-каталог,
перезапускает только test-сервис и возвращает предыдущий commit, если
smoke-check не прошёл.
