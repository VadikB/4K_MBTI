Верни один JSON-объект с массивом checks. Верни по одной строке для каждого запрошенного check_id. Поле required_output описывает форму. Для каждой строки выбери одну форму findings.

- При FAIL верни один или несколько объектов findings. Для каждого укажи точный check_id в requirement_ref, конкретный путь к основанию, причину и тяжесть.
- При PASS, NOT_RUN, INDETERMINATE или TECHNICAL_ERROR верни "findings": [].

quality.clarity — обязательный незащищённый критерий редакционной ясности. Существенную неоднозначность статуса, адресата или единицы оценивай по соответствующему защищённому критерию, который тебе передан. Требования к доказательствам и adversarial_review защищённых критериев действуют в полном объёме. Статус в ответе относится к одной строке. Итог допуска ситуации вычисляет сервер.

Синтетические примеры строк quality.clarity

{"check_id":"quality.clarity","status":"PASS","evidence_paths":["/candidate_as/Материалы/0/Текст"],"reason":"Названы сторона и срок в календарных днях.","findings":[]}

{"check_id":"quality.clarity","status":"FAIL","evidence_paths":["/candidate_as/Материалы/0/Текст"],"reason":"Риторический вопрос затрудняет чтение, единица и смысл вывода ясны.","findings":[{"code":"EDITORIAL_AWKWARD_PHRASING","severity":"non_blocking","paths":["/candidate_as/Материалы/0/Текст"],"reason":"Ответ на риторический вопрос сразу дан в тексте.","requirement_ref":"quality.clarity"}]}

Если запрос содержит clarification_id, скопируй его в верхнее поле clarification_id ответа. Пересмотри только запрошенные строки по приведённым основаниям и материалам той же AS. Для каждой строки приведи согласованные status и findings и объясни решение в reason. Если снимаешь прежнее замечание, укажи в reason, какое утверждение материала его опровергает или делает несущественным даже для редакционной ясности, и сошлись на материал в evidence_paths. Если замечание подтверждается, сохрани его с согласованным статусом и основанием.
