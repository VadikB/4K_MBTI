# Контракт Enterprise Vibe Coding

Действует для всего репозитория. Общение, отчёты и документация — на русском;
команды, пути, API/JSON-поля и машинные идентификаторы сохраняются без перевода.

## Обязательные процедуры

- [Рабочий цикл](docs/evc/agent-workflow.md): разведка, решения, стоп-условия, реализация, отчёт и передача состояния.
- [Матрица проверок](docs/evc/verification-matrix.md): локальный минимум по изменению и обязательный CI перед слиянием.
- [Рецепт артефактов](docs/evc/artifact-recipe.md): выбор контура, версии, валидация, snapshot и откат.
- [Архитектурный контекст](docs/architecture/product-4k/1.0/context.md) и [Registry](docs/architecture/product-4k/registry.md): применимость источников и открытые решения.
- [M1 v1.4](docs/architecture/product-4k/m1/v1.4/README.md): понятийный источник для анализа и проектирования, FROZEN / CURRENT=NO; не автоматический допуск runtime.
- [Шаблон задачи](docs/evc/task-template.md), [ревью](docs/evc/review-checklist.md), [Git-процесс](CONTRIBUTING.md).

До реализации прочитайте README.md, CONTRIBUTING.md и относящиеся к задаче
источники/контракты/тесты. Зафиксируйте прочитанные пути, версии, пробелы, результат,
границы, проверки и откат по рабочему циклу. Уже согласованные решения не требуют
повторного подтверждения; при открытом стоп-условии зависимая работа ожидает владельца.
Агент предлагает и реализует, человек-владелец принимает значимые решения и результат.

## Архитектурные инварианты

- Смысл методологии предшествует коду. Не вводите отсутствующие нормы через prompt, конфигурацию или реализацию. Требования компании не меняют фактическую оценку.
- Целевая ответственность: PM-03 готовит AS, PM-04 исполняет; PM-05 рассчитывает факты, PM-06 интерпретирует, PM-07 представляет. Это не утверждение, что все этапы уже реализованы.
- Различайте UI, сценарий, предметную логику и инфраструктуру. Соблюдайте контракты и владение данными; технологии подключайте через адаптеры. Не создавайте абстракции без конкретной необходимости.
- Сохраняйте связь «источник → правило → PM/LU и контракт → реализация → проверка», для результата — материал, версии и снимок.
- Версии всех этапов M могут корректироваться. Наличие пакета в Git не делает его окончательной нормой. Проектирование M6–M8 разрешено сейчас; постановки и зависимости — в первом эшелоне Change 01. Их функции не считаются выполненными или автоматически дефектными из-за отсутствия.

## Источники и готовность текущей задачи M1/M5

Перед изменением прочитайте [Change 01](docs/architecture/product-4k/1.0/updates/2026-10-01/README.md),
[task manifest](docs/methodology/source-sets/2026-10-01/manifest.json) и только относящиеся
к задаче разделы выбранных файлов. Маршрут чтения — в README поправки. Старый Google
Docs — история происхождения, не обязательный изменяемый вход. Полная ревизия
источников и повторный вопрос об актуальности M1 не требуются; CURRENT не присваивается.

Предметные обязательства находятся в [контрактах](docs/adr/002-cycle-as-dialogue-contracts.md)
и [карте реализации](docs/evc/change01-traceability.md), а не дублируются в инструкциях.
Отчёт архитектора показывает: правило M1 → контракт/данные → фактический код → проверка;
выбранные файлы/хеши, Change 01 и границы PM, актуальные SHA/branch/diff, изменённые пути,
команды и фактические PASS/FAIL/NOT_RUN, зависимости следующей задачи. Различать
подключение источника, проектирование, реализацию и проверку. Уже исправленное не
переделывать: проверить и приложить доказательство. Ссылка в AGENTS закрывает только
доступ к источнику, не соответствие продукта M1.

## Артефакты, совместимость и безопасность

- Предметные определения, содержательные prompts, сценарии, справочники, настраиваемые пороги и правила интерпретации храните вне исходного кода как версионируемые артефакты. Встроенный словарь генератора или перенос в JS не устраняет нарушение.
- В коде допустимы технические алгоритмы, типы и защитные проверки. Предметные значения имеют источник и версию; синтетические test fixtures не являются runtime-настройками.
- Используйте существующий контур по рецепту; если его нет, сначала согласуйте расширение и контракт. Не маскируйте отсутствие обязательного артефакта встроенным fallback. Долг учитывайте в [реестре](docs/evc/artifact-debt-register.md), не расширяя legacy-исключения.
- Опубликованные methodology/scenario/configuration/prompt/agent definitions неизменяемы. Изменение начинается новым draft; начатая оценка использует сохранённый snapshot/checksum, а не текущие настройки.
- Сохраняйте публичный API и данные. Миграция требует явного допуска, плана совместимости и восстановления; feature flag не заменяет этот допуск.
- Не читайте, не выводите, не коммитьте и не передавайте секреты или персональные данные production/test. Автотесты не используют базу разработчика или production; integration — только изолированная БД с test/pytest в имени.

## Передача результата

Один PR — один независимо принимаемый результат. Не смешивайте несвязанный
рефакторинг с изменением поведения. Выполните локальный минимум матрицы, ревью
и полный отчёт рабочего цикла; для пропущенных проверок укажите причину и влияние.
Исправления требуют регрессии; критические пути — integration/HTTP по матрице.
Реальные LLM-вызовы отмечаются llm и не входят в стандартный набор.

Управляющие документы меняются отдельной явно согласованной задачей: запрещено
ослаблять правила внутри обычной задачи ради её приёмки. Перечень — в рабочем цикле.
Делегирование не включается автоматически. Не присваивайте baseline ветке:
нужен неизменяемый commit/tag и весь [чек-лист утверждения](docs/evc/baseline-v1.md).
