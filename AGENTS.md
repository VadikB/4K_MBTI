# Контракт Enterprise Vibe Coding

Эти инструкции действуют для всего репозитория.

Проектная документация и описания задач ведутся на русском языке. Команды,
пути, имена API/JSON-полей, переменные окружения и фиксированные значения
машинных контрактов сохраняются без перевода.

## Перед изменением кода

1. Прочитайте `README.md`, `CONTRIBUTING.md` и относящийся к задаче архитектурный документ.
2. Зафиксируйте ожидаемый результат, область, исключения, ограничения, критерии приёмки и способ отката.
3. Изучите существующие контракты и тесты до предложения новых абстракций.
4. Для работы над несколькими компонентами составьте короткий план и держите в работе только один шаг.

Для нетривиальной работы используйте `docs/evc/task-template.md`. Не начинайте реализацию, пока не принято существенное продуктовое решение или решение по данным, безопасности либо миграции.

## Границы изменений

### Постоянный архитектурный контекст

- Точка входа — `docs/architecture/product-4k/1.0/context.md`; применимость источников и открытые решения — `docs/architecture/product-4k/registry.md`. До значимой задачи прочитайте их и относящиеся к ней контракты.
- Укажите точные версии источников, затронутые PM/LU, контракты, владельцев данных и проверки. Если LU ещё не определена, зафиксируйте пробел, не выдавайте предполагаемую границу за принятую.
- Смысл методологии предшествует реализации. Не вводите отсутствующие нормы через код, конфигурацию или prompt. Требования компании не меняют фактическую оценку.
- Разделяйте ответственность: PM-05 рассчитывает фактические результаты, PM-06 интерпретирует, PM-07 представляет. Подготовкой AS владеет PM-03, исполнением — PM-04.
- Различайте UI, сценарий, предметную логику и инфраструктуру. Не обходите контракты модулей прямым управлением чужими внутренними данными; технологии подключайте через адаптеры.
- Поддерживайте прослеживаемость «источник → правило → PM/LU и контракт → реализация → проверка», а для результата — связь с наблюдаемым материалом, версиями и снимком исполнения.
- Изменение смысла сущности, границ модулей, владения данными, публичного контракта, основания оценки, автоматического перехода, передачи чувствительных данных или границы развёртывания требует зафиксированного решения владельца. Уже согласованные решения не требуют повторного согласования; локальные технические решения принимайте самостоятельно.
- Не создавайте сервисы или абстракции без конкретной необходимости. Целевая архитектура не означает, что существующий код уже ей соответствует.

### Предметные артефакты вне исходного кода

- Методологические определения, содержательные промпты, сценарии, справочники, настраиваемые пороги и правила интерпретации храните как самостоятельные версионируемые артефакты. Используйте существующий контур `assessment_definitions` и публикации, если он покрывает задачу.
- Python реализует загрузку, валидацию и исполнение артефактов. Генерация JSON/Markdown из встроенного Python-словаря с предметным содержанием не устраняет нарушение. Запрет также относится к переносу того же содержания в JavaScript или иной исходный код.
- В коде допустимы технические алгоритмы, типы, механизмы безопасности и проверки контрактов. Предметные значения, которыми они управляются, должны иметь явный источник и версию. Синтетические тестовые fixtures допустимы, но не являются источником runtime-настроек.
- Артефакт должен иметь идентификатор, версию, статус, источник, владельца и контрольную сумму по принятому формату пакета. Новые runtime-пути исполняют точную версию из снимка; неполноту обязательного пакета нельзя скрывать подстановкой встроенных предметных defaults.
- Существующий долг учитывается в `docs/evc/artifact-debt-register.md`. Не расширяйте legacy-исключения; переносите их отдельными проверяемыми задачами с сохранением совместимости. Наличие записи в реестре не подтверждает методологическую корректность правила.

### Совместимость и безопасность

- Одна задача и один независимо проверяемый пользовательский или эксплуатационный результат на pull request.
- Не смешивайте рефакторинг с изменением поведения, если это не требуется для результата.
- Сохраняйте совместимость публичного API и сохранённых данных, если задача явно не разрешает миграцию.
- Никогда не изменяйте опубликованные методологию, сценарий, конфигурацию или пакет промптов на месте. Клонируйте их в новую черновую версию.
- Запущенная оценка обязана использовать сохранённый снимок исполнения и не должна читать изменяемые «текущие» настройки методологии.
- Не читайте, не выводите, не коммитьте и не передавайте секреты или персональные данные production/test.
- Не используйте базу разработчика или production для автоматических тестов.

## Обязательная проверка

Во время реализации запускайте минимально достаточные проверки. Перед передачей pull request выполните:

```bash
npm run lint:js
npm run build:web
npm run test:backend
git diff --check
```

При изменении поведения базы данных также запустите интеграционные тесты на изолированной базе, имя которой содержит `test` или `pytest`:

```bash
TEST_DATABASE_URL=postgresql://... npm run test:backend:integration
```

Исправление ошибки требует регрессионного теста. Изменения публикации сущностей, создания сессий, снимков исполнения, очередей, аутентификации, прав или завершения отчёта требуют интеграционного теста либо теста HTTP-контракта. Реальные вызовы LLM должны быть явно помечены `llm` и никогда не входят в стандартную тестовую команду.

## Ревью и передача результата

Проверьте итоговый diff по `docs/evc/review-checklist.md`. Укажите:

- результат и изменённые файлы;
- выполненные проверки и их точный результат;
- непроверенное поведение и причину;
- последствия для конфигурации, схемы, развёртывания, безопасности и отката;
- минимальный безопасный следующий шаг.

Не называйте ветку базовой версией (baseline), пока для неизменяемого коммита/тега не зафиксировано прохождение всех проверок из `docs/evc/baseline-v1.md`.
