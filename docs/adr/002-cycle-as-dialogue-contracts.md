# ADR-002: контракты Cycle, AS, Dialogue и Results

Дата: 01.10.2026. Статус: проект технического решения для ревью.
Основание: согласованный план включения [Change 01](../architecture/product-4k/1.0/updates/2026-10-01/README.md).
Предметные границы заданы Change 01; имена полей ниже — предлагаемая техническая
конкретизация. Это не публикация API, миграция БД или утверждение реализации.
[ADR-001](001-assessment-platform-architecture.md) сохраняет силу и историю.

## Контекст и решение

Текущий `user_sessions` нельзя автоматически переименовать в Cycle или Session:
сначала нужен явный адаптер соответствия. Новые контракты адресуют Cycle, Session,
AS и версию материала отдельно. Подготовка контрактов и технических проверок
не зависит от новых содержательных Cases или полного алгоритма M7.

## Общая форма сообщения

Для новых контрактов использовать версионированный envelope:
`contract_code`, `contract_version`, `message_id`, `correlation_id`, `source_set_ref`,
`payload_checksum`, `payload`. Для команд — `idempotency_key`; права проверяются
по авторизованному серверному контексту, не по переданному клиентом owner/user ID.

Ссылка `ArtifactRef`: `id`, `version`, `sha256`. Одной формы checksum недостаточно:
получатель разрешает ссылку, сверяет байты/канонический payload и применимость.
Для файлов — SHA-256 исходных байтов; для JSON — существующий контракт
`definition_checksum` из assessment_configuration. Вид вычисления хранить явно,
не подменять один другим. Версия SourceSet не равна версии runtime-конфигурации.

Идентичность: `cycle_id`, `session_id`, `as_id`, `dialogue_id`, `turn_id` — отдельные
непрозрачные идентификаторы; Session принадлежит одному Cycle до первого ответа,
AS — одной Session, Dialogue — одной AS. Один Cycle имеет один внутренний subject ID.
Связи проверяются в транзакции, не только типами JSON. Переопределение профиля,
Case или состава целей начатой AS запрещено. Неизвестное происхождение legacy
помечается как неизвестное и не восстанавливается предположением.

`indicator_targets` принадлежит CaseVersion, AS сохраняет точное множество пар
IndicatorID/M2-ref. Проверяются принадлежность Skill/Component, отсутствие дублей,
сохранение всех целей и допустимая роль. Полнота не заменяется условием count > 0.

Допуск C-34 состоит из отдельных свидетельств: `format_validation`, `case_qa`,
`as_validation`; каждое содержит result PASS/FAIL/NOT_RUN, version проверяющего,
основание, scope и source refs. FROZEN шаблона или PASS лаборатории не заменяет
эти свидетельства. Технический stub может имитировать предметный PASS только
в явно синтетическом тестовом контуре, не в выдаче пользователю.

## Переходы и режимы C-45/C-54

- `interim`: scenario_completed, AS открыта; передаётся граница материала.
  Выход не IA, не входит в агрегирование. Ответ на старую material_revision
  хранится в trace, но не применяется как решение к новому материалу.
- PM-04 решает об уточнении и его тексте в рамках M5 и времени M7. Уточнение
  остаётся в Dialogue; отсутствие ответа — событие, не вымышленный Turn.
  Новое самостоятельное сценарное действие после конца сценария требует другой AS.
- `final_as`: только после атомарного закрытия AS/Dialogue и запрета новых Turns.
  Один логический IA на IndicatorID × AS; повтор обработки возвращает прежний
  результат либо прослеживаемую редакцию, но не новое независимое наблюдение.
- `cycle_calculation`: точный состав входов, даже если расчёт промежуточный.
  Окончательный Results требует закрытого Cycle и завершённых расчётов.
- Пауза и возобновление — отдельные события; не выпускают final IA открытой AS.
  Полные переходы Session/Cycle, оба параметра времени и Additional Session — задача M7.

Хранить EB даже с пустым Evidence; отсутствие IA — отдельная запись причины/покрытия,
не значение L0. Сбой транспорта, timeout, невалидный ответ AI — технический failure,
не INSUFFICIENT_EVIDENCE. Промежуточная неопределённость не является распоряжением PM-04.

## Согласование Results

C-46 и C-56 должны совпасть по Cycle и составу AS; C-56 указывает использованные
итоговые IA и их версии. Несовпадение даёт `COMPOSITION_MISMATCH`, финализация
не происходит. Отсутствующие IA объясняются по каждой цели и не добавляются фиктивно.
Ожидание расчёта не выдаётся за отсутствие Skill Result.

Пять отдельных покрытий: фактические возможности, обоснованные IA, допустимые
вклады, Components со Score, полные Components. Для каждого — числитель,
знаменатель, включённые/отсутствующие IDs и версия состава. План и полный M2
раздельны; неизвестное не превращается в 0, пустой знаменатель — не 100%.

Results один логический на Cycle, расчётных версий несколько с сохранением истории.
Report ссылается на точную версию. Четыре исхода Skill, ноль/отсутствие и
NOT_COMPARABLE сохраняются без округления Score в Level. Recommendations не входят
в первый базовый Report; CHECK M4 относится только к их будущему включению.

## Хранение, повторы и ошибки

Предлагаемые записи: immutable CaseVersion/ProfileSnapshot/AS snapshot;
Cycle и Session membership; append-only Dialogue Turns/events/materials;
processing requests/results и AI trace; логический Results + расчётные версии.
Физические таблицы, индексы и FK оформляются отдельной expand-миграцией до кода записи.

Для Turn обязательны scoped idempotency key и payload hash. Повтор с тем же ключом
и payload возвращает тот же Turn; другой payload — конфликт. Закрытие AS и добавление
Turn сериализуются на состоянии AS. Последовательность выдаёт сервер. Повтор
после commit/падения worker не запускает независимое наблюдение; уникальность
финального результата защищается БД. Нельзя дедуплицировать разные ходы лишь по тексту.

Коды ошибок для нового пути: `SOURCE_UNRESOLVED`, `CHECKSUM_MISMATCH`,
`TARGET_SET_MISMATCH`, `ROLE_NOT_ALLOWED`, `AS_NOT_ADMITTED`, `AS_CLOSED`,
`STALE_MATERIAL`, `IDEMPOTENCY_CONFLICT`, `COMPOSITION_MISMATCH`, `AI_FAILURE`.
Ошибки включают безопасную причину и correlation ID, не содержат PII/секретов.

AI trace сохраняет фактические provider/model, prompt ref/hash, параметры,
output schema и handler version, request/material revision, статус/ошибку.
Решение о новой внешней конфигурации применяется только к новому прогону;
при недоступности закреплённого механизма — явный failure, не скрытая подмена.

## Совместимость, внедрение и откат

Новый путь получает отдельную версию контрактов и явный opt-in; legacy читает
собственный снимок/адаптер с обозначенными ограничениями. Нет массового backfill
и автоматического превращения user_sessions в Cycle. До включения записи — карта
данных и expand-миграция, проверенная на изолированной test-БД. Feature flag не
заменяет этот план. Откат выключает создание новых прогонов, сохраняет новые записи
и поддержку их чтения; старые версии и снимки не изменяются.

## Проверки и статус

Сценарии T01–T12 и текущее доказательство — в
[матрице](../evc/change01-traceability.md). Новые контракты здесь спроектированы,
не реализованы и не проверены выполнением. Начало алгоритмов M6/M7/M8 не требует
завершения всех соседних модулей: стыки проверяются fixtures/stubs. Общий прогон
требует исправленных входов, реализованных потребителей и выполненных технических
проверок. Содержательная приёмка дополнительно требует новых Cases и экспертных GC.
