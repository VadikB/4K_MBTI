# ADR-003: ProgramDefinition и полное удаление данных

- Статус: принято владельцем продукта, техническая реализация в работе.
- Основание: уточнение ADM30/ARCH30 и ADD01 от 30.10.2026.
- Область: подключение программы оценки, полное удаление организации/аккаунта,
  незавершённый Cycle при удалении и переносе.

## ProgramDefinition

`ProgramDefinition` — минимальная версионируемая продуктовая связка точной
`assessment_configuration`, точного `catalog_version_id`, `source_refs` и списка
точных опубликованных версий ролей. Версия имеет `draft → published → retired`; содержимое `published` и
`retired` неизменяемо. Единственное разрешённое изменение опубликованной строки —
`published → retired`.

Подключение организации хранится отдельной историей. Новое подключение закрывает
только текущую связь; сохранённые source bindings назначений и начатые Cycle не
переписываются. `retired` запрещает новые назначения и подключения, но сохраняет
историю. При одной допустимой роли она выбирается автоматически; при нескольких
назначение обязано передать одну из разрешённых версий. Пользовательские access
roles не добавляются.

Техническая публикация выполняется release-командой
`scripts/publish_assessment_program.py`; без `--publish` она только валидирует
точные опубликованные зависимости и checksum. Фактическая публикация и выпуск
девяти кейсов не входят в текущий запуск (`artifact_publish=false`). Старые
`organization_assessment_pilot_bindings` временно читаются только для совместимости
организаций, ещё не переподключённых через программу. Для пилота публикуется
только утверждённая версия роли «Специалист» и подготовленные материалы пилота,
ранее называвшиеся Sales. Это ограничение конкретной программы: механизм выбора
ролей и остальные роли продукта не удаляются. Продуктовый ответственный определяет
состав, методолог согласует методологические изменения, архитектор выполняет
техническую публикацию через release-процесс. Новая роль «технический специалист»
не вводится.

Суперадминистратор подключает только `published`-версию через интерфейс продукта.
Скрипт публикации не является пользовательским способом подключения. Подключение
не заменяет заполнение и подтверждение обязательных сведений организации.

## Полное удаление

Пользовательский сценарий один: необратимое полное удаление. Деактивация остаётся
отдельной обратимой административной операцией и не является удалением. Purge
должен иметь две области: организация вместе с показанными orphan-аккаунтами и
отдельно выбранный аккаунт, в том числе без membership.

Перед исполнением сервер строит точный dependency plan, возвращает состав и
fingerprint. Исполнение повторно строит план под блокировкой и отклоняется при
изменении fingerprint. Идемпотентный operation id хранится только в минимальном
техническом tombstone без email, анкет, credentials и истории. После удаления
выполняется отрицательная проверка всех строк области и положительная проверка
сохранности контрольной организации.

Повтор команды после потерянного HTTP-ответа читает receipt и возвращает успех,
не требуя уже удалённую цель. Для организации сохраняется только SHA-256 её кода:
bootstrap из `ORG_NAMES` не может автоматически восстановить удалённую организацию,
а явное повторное создание через product UI начинает новый путь и снимает hash-
tombstone. Текущий аккаунт суперадминистратора и аккаунты, всё ещё объявленные в
`SUPERADMIN_EMAILS`/`ORG_ADMIN_EMAILS`, не предлагаются для отдельного удаления:
сначала владелец конфигурации должен убрать сохраняющее доступ объявление.

Незавершённые Cycle удаляются физически вместе с зависимостями; terminal status
не создаётся, расчёт и отчёт не запускаются. FK родительских `organizations` и
`users`, транзакционная блокировка и tombstone закрывают поздние DB-записи;
очереди входят в dependency plan. Повторное добавление email/кода создаёт новые
идентификаторы и не может восстановить старое membership, пароль, согласия,
назначения или bootstrap-права.

## Управляемые копии

В runtime-коде не найдено постоянного файлового/object storage пользовательских
данных: CSV сохраняется как DB revision, PDF/ZIP строятся в памяти или временном
каталоге и отдаются в ответе. In-process caches не являются постоянным хранилищем
и очищаются рестартом процесса; очереди постоянны в PostgreSQL и удаляются планом.

Общие инфраструктурные backup PostgreSQL находятся вне этого репозитория. Удалять
общий backup ради одной организации нельзя. Реализован fail-closed контур:

- PII-free JSONL intent хранится по `DELETION_LEDGER_PATH` вне восстанавливаемой БД;
- intent содержит operation id, тип/числовой id цели, fingerprint и время, но не
  email, анкеты, credentials или историю;
- в БД хранится только `data_deletion_receipts`; после restore старого backup
  поздний receipt отсутствует;
- startup до запуска API/workers сверяет ledger и receipts и завершается ошибкой
  `DELETION_LEDGER_REPLAY_REQUIRED`, если tombstone не применён;
- `scripts/replay_deletion_ledger.py` имеет read-only default и явный `--apply`,
  повторно удаляет восстановленную цель либо фиксирует уже отсутствующую цель,
  затем проверяет полную reconciliation.

Изолированная restore-модель подтверждает блокировку startup и успешный replay.
Product-исполнение доступно при provisioned внешнем ledger с правами `0600`,
мониторингом и runbook; без `DELETION_LEDGER_PATH` production purge fail-closed.
Это не специальная резервная копия удалённых данных и не основание хранить их
90 дней. Обычная таблица в той же БД
не считается ledger, потому что старый backup не содержит поздний tombstone.

## Перенос

Перенос без удаления сохраняет аккаунт. Старая оценка не перепривязывается;
для `prepared`, `active`, `paused` и `interrupted` закрытие сбора выполняется
действующим M7 с причиной `organization_transfer` в старом контексте. Уже
`collection_closed` или `calculation_pending` не блокируют перенос: обработка
остаётся закреплена за прежними `organization_id`, Cycle и source bindings.
Назначение старой организации отзывается, а в новой организации нужны новое
назначение, новый контекст и новый Cycle. Универсальный `cancelled` не вводится.
Полное удаление и перенос остаются разными командами.
