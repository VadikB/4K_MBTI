# Матрица проверок EVC

Обязательна по [AGENTS.md](../../AGENTS.md). Таблица задаёт локальный минимум
до создания PR; при сочетании типов применяется объединение требований.
Во время реализации сначала запускаются затронутые тесты. Полный применимый набор
выполняется для точного SHA кандидата перед передачей, а не после каждой карточки.
Его повторяют, если изменилось проверенное основание, разрешён конфликт или обнаружена
ошибка. Больше проверок нужно при новых сбоях или обоснованном риске.

Класс риска путей помогает выбрать ранний локальный набор, но не отменяет строки
матрицы и обязательный CI: `low` — только docs без runtime-содержания; `medium` —
frontend, tooling и изолированная прикладная логика; `high` — БД, auth/права,
публикация/snapshot, CI/release/deploy и критические runtime-контракты. При сочетании
применяется максимальный класс и объединение проверок.

| Тип изменения | Локальный минимум перед PR |
| --- | --- |
| Только Markdown / docs | `git diff --check`; проверка локальных ссылок, путей и существования описанных команд; содержательное review согласованности |
| JS без изменения поведения | `git diff --check`, `npm run lint:js`, `npm run build:web` |
| JS с изменением поведения | Предыдущая строка + затронутые frontend-тесты (`node --test tests/frontend/*.test.mjs` для существующего набора); при отсутствии покрытия — адресный тест/ручной сценарий и его ограничения |
| HTML/CSS и визуальные изменения | `git diff --check`, визуальная проверка затронутого сценария; сборка при затронутых bundle/entrypoints; при изменении JS — соответствующая строка выше |
| Backend-логика, загрузчики, сборщики | `git diff --check`, `npm run test:backend`; регрессия для исправления ошибки |
| Предметный пакет / prompt | Проверка формата, ссылок, checksum и сохранения содержания из [рецепта](artifact-recipe.md); затронутые тесты потребителей; при изменении Python — backend-набор |
| Схема, миграция или поведение БД | Backend-набор + `TEST_DATABASE_URL=… npm run test:backend:integration` на изолированной БД; совместимость старых/новых данных и восстановление по плану |
| Публикация сущностей, сессии, snapshots, очереди, auth, права, завершение отчёта | Backend-набор + интеграционный либо HTTP-контрактный тест изменённого пути; если меняется поведение БД, integration обязателен |
| Транспорт/поведение LLM | Backend-набор и контрактные тесты с подставным gateway; реальные вызовы только с маркером `llm`, отдельно от стандартных тестов |
| Зависимости, CI, сборка, deploy | `git diff --check` + затронутые lint/build/test и проверка конфигурации/процедуры; точный набор до реализации фиксируется в задаче |

В проекте сейчас JS, отдельного TypeScript typecheck нет. При появлении TypeScript
нужно определить проверку типов; нельзя объявлять `lint:js` достаточным для TS.
Изменение runtime-артефакта `.md` (например prompt) не является «только docs».

## Команды и ограничения

- `npm run test:backend` исключает integration, e2e и llm.
- `npm run test:backend:http` запускает существующие HTTP-контракты без реального LLM.
- `TEST_DATABASE_URL=… npm run test:backend:integration` требует отдельную БД,
  имя которой содержит `test` или `pytest` и не совпадает с рабочей DB_NAME.
  Не использовать базу разработчика, production или общий test-контур с рабочими данными.
  Пропуск integration из-за отсутствия URL не считается успешным прогоном.
- Реальный LLM запускается явно, например `.venv/bin/python -m pytest -m llm tests/llm`.
  Его необходимость, стоимость и допустимые данные задаются задачей; отсутствие
  реального прогона не доказывает качество оценивания или методологическую валидность.
- `npm run build:web` очищает `web/dist` перед сборкой. Сначала проверить Git и
  сохранить посторонние локальные файлы; не терять пользовательскую работу ради проверки.

Конкретные команды брать из [package.json](../../package.json), а правила из
[tests/README.md](../../tests/README.md). Команда в отчёте записывается без секретов;
для тестовой БД допустим редактированный URL с указанием изолированного контура.

## Обязательный CI перед слиянием

Локальный минимум не отключает [GitHub workflow](../../.github/workflows/backend-tests.yml).
В текущем CI для каждого PR и кандидата merge queue обязательны успешные jobs
`coordination`, `frontend`, `pytest` и `full-verification`:

- frontend: аудит зависимостей, lint, frontend regression tests, сборка и совпадение `web/dist`;
- pytest на событии `pull_request`: быстрые unit- и HTTP-контракты на отдельном
  PostgreSQL 16; integration и browser на этом событии не запускаются.

Обязательный job `full-verification` не запускается для draft PR. Он впервые
запускается при создании PR сразу не в draft либо при переходе draft PR в
`Ready for review`, затем — после каждого нового commit, пока PR остаётся Ready.
Job выполняет integration и browser acceptance на изолированной БД в
`pull_request`- или `merge_group`-контексте. Unit и HTTP выполняются один раз быстрым
job `pytest`.
Новый commit после успешного полного прогона Ready PR делает доказательство
устаревшим и запускает workflow для нового head; незавершённый прогон прежнего
head отменяется. Активный ruleset не разрешает merge без checks `frontend`,
`pytest` и `full-verification`.

Для документального PR полный CI также сохраняется. Job `deploy-test` на PR
ожидаемо пропускается: он применяется после push в main, а не является доказательством
проверенного развёртывания кандидата. Проверять результат для актуального head и
целевой ветки; после изменения base или разрешения конфликтов проверить CI заново.
Для `main` действует ruleset `Protect main and require full verification` (ID
`26191885`) без bypass, только со squash merge и обязательным актуальным head.

Workflow `CI` запускается на `pull_request`, `merge_group` и push в `main`: на PR и
кандидате очереди выполняются `coordination`, `frontend` и быстрый `pytest`, а на push
в `main` — только `coordination` и `deploy-test`.
В draft job `frontend` выполняет весь набор, кроме отложенного шага
`Verify application release`. Переход в `Ready for review` повторно запускает
быстрые jobs `frontend` и `pytest` для того же head, включает release gate и
запускает `full-verification`. Merge без нового согласованного номера продукта
остаётся запрещён. Workflow `Full verification` реагирует на `merge_group` и события
PR `opened`, `reopened`, `synchronize`, `ready_for_review`; для PR job выполняется
только при `draft == false`. Ручная метка не требуется.

## Отчёт и сбои

Для каждой применимой проверки указать команду, результат/exit code и доказательство.
Для невыполненной — что, почему, влияние на готовность и следующий способ проверки.
Различать «passed», «failed», «не запускалось», «пропущено runner» и «не применимо».
Проверка должна относиться к передаваемому содержимому; результаты предыдущего
неизменённого шага можно переиспользовать с указанием области и commit.

Локализовать падение по [рабочему циклу](agent-workflow.md), не расширяя задачу
без основания. Обязательный CI failed/pending не заменяется локальным успехом.
Для baseline дополнительно нужен весь [чек-лист утверждения](baseline-v1.md):
CI сам по себе не заменяет развёртывание, человеческую приёмку, откат и неизменяемый тег.
