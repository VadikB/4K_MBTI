## 3. Цель, состав и конкретный маршрут-кандидат

Предлагаемая цель: ограниченный функциональный пилот сбора материала по доступным
частям конструкта для specialist_expert в одном frozen профессиональном контексте.
Не обещать полную оценку четырёх компетенций, уровни всех Skills или Reliability.
Для следующего PATH проверяется доставка первой AS, а не завершение всего этого Cycle.

Полный нормативный знаменатель61 сохраняется всегда. **Предлагаемый** плановый
состав39 задаётся до взаимодействия только после рассмотрения матрицы и её
содержательных условий методологом. Он не становится утверждённым от совпадения
с union каталога. До согласования оба approval в JSON=PENDING, runtime_authorization=NONE.

Маршрут-кандидат воспроизводит существующее техническое ранжирование максимального
нового вклада/распределения по компетенциям/planned max/CaseID. Это прозрачный
отправной вариант для review, **не восстановление удалённого плана run96abd1** и
не доказательство методологической пригодности порядка. Не генерировать его целиком заранее.

## 4. Условные и отсутствующие цели

Все55 строк — запроектированные возможности, не факты возникновения, Evidence или IA.
Каждая привязана к source AS JSON/pointer/hash, материалам, местам сценария,
наблюдаемому условию, инвариантам и риску. Полная матрица включает также22 отсутствующих.
Structured branch/event поля у этих строк null; это **не** вывод о безусловности:
содержательные условия сохранены verbatim и требуют проверки после персонализации.

Особенно значимы:

- K2.I08 в SPEC.03: после E01_UPDATE знание распределено неравномерно; E02_TRANSFER
  допускает реальную передачу. Есть другая проектная возможность в SPEC.08,
  но до её предъявления/действия это не фактическая альтернатива и не Evidence.
- K3.I10 в SPEC.04: E01_REVIEW — участник сам проверяет существенное предположение,
  а не получает готовый тест; реплика согласия сама по себе недостаточна.
- K3.I11 в SPEC.04: E02_REVISION применим, если отклик выявил ограничение.
  Другого Case с этой целью нет. Ветвь нельзя принудительно вызвать отказом персонажа;
  если её нет, сохраняется ограничение, а не выдуманный IA/повторный шанс.
- K1.I11 в SPEC.08: возможность работы с риском искажения не сводится к одной
  ветви коррекции; E02_CORRECT допустим лишь при фактическом искажении.
  Нельзя искусственно приписать ошибку участнику ради наблюдения.
- K4.I10 в письменном SPEC.07: проверка доступна аналитически на имеющемся материале;
  недоступный реальный эксперимент не предъявляется как обязанность участника.
  Методолог подтверждает границы интерпретации этой реализации.

## 5. Методологическое обоснование и ограничения результата — на согласование

Основание допустимости такого **вида** плана — M7.2.2, прежний ARCH-A05 и решение
об ограниченном каталоге; конкретное обоснование предлагается как разведочный,
ограниченный сбор по доступным целям, а не сокращённая норма компетентности.
Матрица позволяет проверить, какое самостоятельное действие и при каких условиях
вообще возможно, а не просто посчитать39. Предлагается по одной самостоятельной
проектной возможности на целевой Indicator; достаточность/повторность должен
подтвердить методолог, технический default required_final_ia_count=1 не является
его решением. Повтор одного Indicator не повышает его вес/покрытие.

По design-составу все14 Skills имеют хотя бы одну потенциальную цель. Только
K1.4/K3.1/K4.3/K4.4 имеют весь состав Indicators в каталоге; это ещё не полный
фактический Score даже для них. Нельзя заранее объявить все Scores полными либо,
наоборот, запретить допустимый полный результат отдельного Skill, если M6 реально
подтвердит весь его обязательный состав и требования. Разрезы считать отдельно.

Обязательные ограничения: план/catalog opportunity ≠ возникшая возможность ≠
обоснованный IA ≠ допустимый вклад. M6/M8 сохраняют полный/частный Score, результат
без Score и отсутствие Skill Result; отсутствие/INSUFFICIENT_EVIDENCE не заменяется
нулём, L0 не приписывается за пробелы. Даже100% утверждённого пилотного плана не
есть100% M2. Confidence не множитель, Reliability не доказана. Между Cycles ничего
не суммируется ради покрытия; новый профессиональный контекст не подменяет frozen profile.

Проект пользовательского обещания для продуктолога: «Ограниченный пилот собирает
материал по отдельным сторонам навыков в рабочих ситуациях. Результат отражает
только фактически полученные и допустимые основания; полнота и отсутствующие цели
показываются отдельно. Полная оценка всего конструкта не гарантируется».
Это текст для review, не опубликованный prompt/briefing и не новый runtime copy.

## 6. Необходимая согласованность server / UI / runner — дизайн, не fix

`coverage_status=READY/LIMITED/NO_ROUTE` оставить характеристикой покрытия;
допуск старта — отдельное серверное решение по **точному** согласованному плану.
Ни READY сам по себе, ни любой LIMITED не дают разрешения.

Предлагаемый общий PM-04 readiness contract (нужен технический review до реализации):

В данных различать full_target_set61, утверждённый planned_target_set39 и22 цели
вне плана. Пробел внутри утверждённого плана — отдельная причина, не «вне плана»;
невозникшую условную возможность не удалять после ответов. Существующий
uncovered_target_ids нельзя незаметно переопределить при добавлении двух разрезов.
Совместимость полей/версии определяется T1, не этим review JSON.

1. Сервер разрешает immutable plan ref и свидетельства продуктолога/методолога,
   связанные с точными program/config/catalog/Case/M2 refs, goal/плановыми целями,
   порядком/условиями/ограничениями, timing basis и checksum утверждённого payload.
   Локальный JSON проекта или клиентский флаг не являются таким свидетельством.
   Существующий planning artifact draft QA не получает assessment-допуск автоматически.
2. Проверяет owner/tenant, активное exact assignment/binding/questionnaire, frozen
   profile и совпадение operation→profile→Cycle; роль и все источники/checksums.
3. План непустой, решение/AS относятся к exact plan revision/Cycle/Session;
   Cycle допускает первый старт. Для LIMITED требуется именно этот approved pilot
   plan, совпадение39 целей/ограничений и отсутствие иных блокеров; неизвестный
   либо неподтверждённый LIMITED, NO_ROUTE, mismatch или revoked scope блокируют.
4. Сохраняет обязательный final admission каждой AS: generation/tester/challenger,
   штатный repair только в существующих границах, конечный кандидат/compiled Case/
   saved AS с точными refs. PASS или PASS_WITH_WARNINGS допускается только при
   admitted_for_participant=true и всех обязательных checks; INCOMPLETE/FAIL и
   недопущенная AS всегда блокируют. Case QA не заменяет AS admission.
5. Проверяет effective7200/259200 и **версионный источник настройки в exact scope**,
   до первой AS/первого старта; время не начинается от подготовки. При первом
   explicit start запускаются Session/Cycle и календарное окно, при возврате
   проверяется существующее состояние/фактический остаток. Нет нового cut-off по
   planned duration и нет автоматического увеличения бюджета. Правила pause/wait
   и continuation неизменны.
6. Все проекции возвращают одинаковое authoritative can_start/блокеры и refs,
   не вычисляют право независимо в JS/admin. Participant показывает ограничения
   утверждённого пилота; admin различает ограниченный допущенный план и блокер.
   Start POST повторно проверяет всё в транзакции, не доверяет ранее прочитанному UI.
7. Runner проверяет тот же серверный допуск и основание exact LIMITED, а не заменяет
   READY на `READY || LIMITED`. Стадии/lineage/времена/hash chains/start201/readback/
   первая предъявленная AS/ответы0 остаются обязательны; все отказы сохраняются до cleanup.

Сейчас code/UI допускают разные проекции, runner READY-only. Исправления потребуют
проектирования versioned plan/admission binding и additive совместимости в существующем
контуре; нельзя тихо добавить непроверенный ref в published source_refs_json.
Новые draft definitions/immutable snapshots применяются только к новым Cycles;
исторический prepared/active Cycle не переписывается. Схема/миграции/публичный формат
при необходимости отдельно согласуются архитектором; этот документ их не разрешает.

PILOT-120 уже выбран, но его привязка в последнем owned run не исполнена: фактически
3600/259200 method_default. Ни увеличение времени, ни approved plan не исправляют
покрытие магически. Наличие7200 на другой организации/конфигурации не наследуется.
Здесь существующие configure_* скрипты **не запускаются**, даже dry-run может
вызывать ensure_schema. Будущая scoped revision/readback — отдельное разрешённое
действие; нынешняя постоянная БД и старый Cycle не меняются.
