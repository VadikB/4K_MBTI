## Реализация и диагностика

- `Api/m6_contracts.py`, `Api/m6_evidence_service_v2.py` и `Api/m6_validation_retry.py` собирают сохранённый Fragment из дословного кандидата и проверяют ссылки, критерии и границы диалога. После ошибки определения места повтор сохраняет ID проблемного фрагмента. Уточнение неоднозначной цитаты должно содержать исходную цитату в том же ходе.
- `validation_attempts` содержит номер попытки, код и путь каждого найденного нарушения. Записи исходного обмена с провайдером остаются в техническом аудите `provider_attempts`. Контрольная сумма `assembled_analysis` соответствует сохранённому анализу, который отдельно доступен через `m6_analysis_revisions`.
- `assessment_definitions/prompts/m6_evidence/v1.0.2/`, `Api/m6_package_v2.py`, манифест Cycle, `enqueue_handoff` и воркер фиксируют `M6.EvidenceInput/2` и `M6.EvidenceCandidate/2`. C-54 ссылается на ту же сохранённую ревизию Evidence. В QA-фикстуре GC обновлены контрольные суммы технических зависимостей от кода. Методологические источники и экспертные данные этой фикстуры взяты из предыдущей версии.

Исправленный Fragment должен остаться связан с тем же IndicatorID через наблюдение и Evidence. Явный пересмотр фиксируется через `attribution_notes` для того же индикатора с объяснением и ссылкой на исходный Turn. При `unclear` сохраняется наблюдение и указывается неустановленный признак. Проверка относится к повтору одного вызова механизма, а исходно обоснованный пустой разбор по-прежнему допустим. | Ответы модели | Воркер на `31c1099c` | Воркер после исправления |
| --- | --- | --- |
| «уточню» с `start`, затем пустой разбор | `succeeded`, ревизия с 0 Fragment, 0 BS, 0 Evidence | `failed`, без ревизии. На первой попытке `extra_forbidden` (`fragments.0.start`) и `M6_FRAGMENT_QUOTE_AMBIGUOUS` (`fragments.0.quote`). На второй `M6_FRAGMENT_REPAIR_MISSING` (`fragments`). |
