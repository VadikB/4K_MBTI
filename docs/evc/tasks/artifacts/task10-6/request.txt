ЗАДАНИЕ 10.6 — ИСТОРИЯ НОВЫХ ОЦЕНОК И ПОВТОРНЫЙ ДОСТУП К M8 REPORT/PDF
Редакция 1. Дата: 05.10.2026. Зависимости: 10.4; общий сценарий использует 10.5.

1. РЕЗУЛЬТАТ

После завершения оценки пользователь может выйти, войти снова, открыть «Мои отчёты», найти свой Cycle и открыть/скачать сохранённый M8 Report. Главный экран и история согласованы. Работают несколько Cycles и revisions без смешения результатов.

2. ОСНОВАНИЕ

REV-03: Api/routes.py::_build_dashboard читает m8_reports, но переход web/js/screens/dashboard.js → openReports → loadProfileSummary вызывает /users/{id}/profile-summary. Его history строится из user_sessions. web/js/screens/reports.js открывает отчёты/PDF через legacy session_id. Для одной новой M8-записи и нуля старых сессий dashboard показывает 1, история — 0.

Ответственность: M8/PM-07 и owner read API; фактические результаты PM-05/PM-06 не пересчитываются.

3. РЕАЛИЗАЦИЯ

— Добавить или исправить owner-scoped список оценок с Cycle ID, состоянием обработки, датами, идентификаторами Results/Report и применимой revision. UI использует этот контракт для новых оценок.
— Развести сущности: одна оценка/Cycle, Results revision, Report revision. Зафиксировать семантику счётчика в UI и API. Для списка оценок регенерация представления одного Cycle не увеличивает число пройденных оценок; версии при необходимости представлены внутри его истории.
— Показать предусмотренные состояния: результат готовится, Report доступен, техническая ошибка/восстановление. Сбой рекомендаций не скрывает готовый базовый Report и не становится недостатком участника.
— Открытие из списка и PDF используют реальные Cycle/Report IDs, а не session_id другого контура. Выбранная строка ведёт к соответствующему сохранённому результату. Определить, где открывается последняя версия, а где явно выбранная историческая.
— GET, reload, повторный вход и скачивание не создают новую оценку, IA, Results или Report revision. Явная регенерация сохраняет прежний Results и историю, а выдача старых рекомендаций проходит защиту 11.1.
— Проверять owner, tenant и аудиторию отчёта. Не показывать QA-Cycles, административные или customer-представления через список assessee. Ссылки на чужие IDs не обходят защиту.
— После logout/смены пользователя очищать список, текущий Report и кэш; две вкладки корректно сверяются с сервером. Пустое состояние истинно только при отсутствии доступных оценок соответствующего контура.
— Существующую legacy-историю сохранить без удаления/массовой миграции. Если она остаётся доступной, её идентификаторы и обработчики не смешиваются с новыми. Удаление legacy UI/API не является целью задачи.

4. ПРИЁМКА

H10.6-01: одна завершённая M8-оценка, ноль legacy-сессий: карточка присутствует, счётчики согласованы, Report и PDF открываются из истории.
H10.6-02: настоящий logout → новый login → «Мои отчёты» → нужный Report/PDF. Нельзя заменять этот сценарий прямым URL из памяти теста.
H10.6-03: два независимых Cycle одного пользователя видны отдельно; их Results/Report/material refs не перемешаны.
H10.6-04: две revisions Report одного Cycle не становятся двумя пройденными оценками. Выдаётся ожидаемая версия; прежняя история сохранена.
H10.6-05: processing, отсутствие результата, сбой генератора рекомендаций и готовый базовый Report различаются корректно.
H10.6-06: anonymous и другой участник не получают список/JSON/PDF владельца; QA/admin/customer данные не попадают в пользовательский список.
H10.6-07: повтор GET/reload/download не меняет число IA/Results/Reports и их checksums; историческая защита 11.1 действует.
H10.6-08: смена пользователя очищает UI; совместное наличие старой истории не искажает новую.
H10.6-09: HTTP/DB/browser проверки выполнены на изолированной PostgreSQL, текущая сборка frontend воспроизводится, CI финального commit пройден.
