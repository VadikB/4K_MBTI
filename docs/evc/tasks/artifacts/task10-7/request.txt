ЗАДАНИЕ 10.7 — ОБЩАЯ ПРИЁМКА ПУТИ M1–M8 ПОСЛЕ ДОРАБОТОК
Редакция 1. Дата: 05.10.2026. Зависимости: 10.4, 10.5, 10.6, 11.2, 8.1 на одной сборке; сохраняются 11.1, 10.2 и 10.3.

1. РЕЗУЛЬТАТ

Получить доказанное состояние общей сборки: что работает технически, какие предметные ограничения остаются и разрешён ли следующий этап. Главная новая трасса начинается с обычного участника без готового M4 и заканчивается повторным доступом к своему сохранённому Report/PDF через историю после нового входа.

Не подменять эту задачу подсчётом unit-тестов или запуском прежнего browser suite без расширения. M1/M2 — источники/правила, M3/M4 — подготовленный профиль, M5/M7 — прохождение, M6 — оценивание/допуск, M8 — сохранённый результат и представление. Проверяются стыки, а не просто наличие модулей.

2. СБОРКА И СРЕДА

— Зафиксировать единый commit, версии пакетов/источников, browser/Python/PostgreSQL/Typst и режимы каждого AI-механизма. Переснять manifest именно этого дерева; не включать отсутствующие старые web/dist-файлы.
— Сохранить entrypoint 10.2: два независимых запуска с пустых принадлежащих тесту БД, повтор bootstrap/seed/restart без потери данных, реальные main/HTTP/auth/workers.
— Базовый seed вправе создать синтетическую организацию, допущенный аккаунт, административные настройки, опубликованные источники и отдельно отмеченные case fixtures. Для главной новой трассы seed НЕ создаёт пользовательские UserContext/M4, Cycle/AS/Turns/IA/Results/Report. Перед первым пользовательским действием это проверяется read-only SQL.
— Подменять только явно объявленную AI-границу. Auth, owner API, DB, worker, orchestration, admission, Results/C-67 и PDF — настоящие. Контекст участника формируется штатными действиями, finalization не выполняется скрытым admin/SQL вызовом.
— Часы/короткие временные параметры допустимы только как отмеченный тестовый режим до начала сценария; нормативные defaults не менять. Пропущенный тест не считать PASS.

3. ОБЯЗАТЕЛЬНЫЕ СЦЕНАРИИ

G10.7-01. Новый обычный участник: вход с существующим разрешённым механизмом → контекст и выбор роли → подтверждение → M4 → старт Cycle → диалог, нужное уточнение → завершение → обработка → M8 Report/PDF. Новое ТЗ входа по коду из UX-чата этой задачей не внедряется. Проверить owner/org/version refs и неизменяемый snapshot.

G10.7-02. После G01 настоящий logout, очистка клиентского состояния, новый login → «Мои отчёты» → тот же Cycle/Report/PDF. История не пуста из-за отсутствия legacy-сессий. JSON/revision/checksum соответствуют сохранённому результату; повторный вход не запускает оценку заново.

G10.7-03. Новая независимая оценка по действующему допуску: новый Cycle, собственный профиль/материал; в истории два результата. Явная регенерация представления одного Cycle сохраняет Results и не увеличивает число пройденных оценок. Данные Cycles не смешиваются.

G10.7-04. Полный повтор шести сценариев 10.3 на этой сборке: A/T11-10, B/Additional Session, C1/реальная фоновая вкладка и бюджет, C2/deadline на паузе/закрытом браузере, recovery/lost response/две вкладки, отдельно разрешённый synthetic character. Новые тесты не заменяют старые. Не расширять их доказательность за фактически выполненные действия.

G10.7-05. Профиль и права: anonymous/owner/другой пользователь/другой tenant; GET/PATCH/confirm/start/history/Report/PDF. Owner может выполнить разрешённый путь, чужие запросы не выдают данных и не изменяют их. Новая организация/конфигурация не выбирает старый чужой по области M4. Отказ не содержит персональных сведений.

G10.7-06. Контекст рекомендаций: реальный M4 из G01 → сохранённый Results → непустая безопасная проекция → релевантный application_context в UI/C-67/PDF. Отдельно пустой/частичный контекст и отсутствие идентифицирующих полей. Изменение текущего профиля не меняет исторический.

G10.7-07. Основания/типы: положительная выдача есть; IE перед допустимым IA исключён; нет основания ≠ технический сбой; justified L0 не превращается в закрепление успеха; три типа допускаются только там, где обоснованы. Исторический неподтверждённый C-67 не обходит фильтр; regenerate создаёт новую revision без изменения Results.

G10.7-08. Admission 8.1: матрица содержательных контрпримеров выполнена на реальных сохранённых входах. Проверены допустимая вариативность, значимая несопоставимость, влияние уточнения, отдельная интерпретация без среднего и технический отказ. Решения/ограничения доходят до отчёта.

G10.7-09. Числа/состав: независимо заданные ожидаемые значения для full_score, partial_score, result_without_score, no_result; ноль ≠ отсутствие результата; нет смешения Score/Level/Target; состав покрытия не сокращён задним числом. Повторные IA/AS/Cycle не удваивают вклад. Полное покрытие всех четырёх исходов может быть распределено между DB/HTTP/browser; область каждого доказательства указана честно.

G10.7-10. Ошибки/устойчивость: восстановление после reload/потери ответа, повтор ключа, обработка worker failure и предусмотренного retry. Техническая ошибка не становится предметным результатом. Чтение готового отчёта не зависит от доступности AI и не запускает скрытый пересчёт. Нет утечки предыдущего пользователя через кэш/вкладки.

G10.7-11. Рабочие входы: отдельный read-only реестр применимых case versions, ролей, QA-допусков, открытых решений и покрытия маршрута для целевой группы. Пять WORKING-кейсов и тестовые FROZEN-копии не считаются доказательством рабочего допуска. CASE-TDISC-04 не разрешать без предметного решения по открытой ветви. Проверку реальной БД/стенда делать только через разрешённый конфигурационный доступ без чтения персональных строк; при отсутствии доступа отметить NOT_VERIFIED. Не менять статусы источников автоматически.

G10.7-12. Real-provider smoke: если уже предоставлены разрешённые доступы, согласованный провайдер и лимит затрат, провести отдельный минимальный синтетический путь с реальными AI-адаптерами M5/M6/M7 там, где они используются. Зафиксировать вызовы/модель/версии/режим, длительность, ошибки и фактический результат. Deterministic Recommendations не требуют LLM. Не искать секреты и не включать платные вызовы без существующего допуска. Если его нет — остальные сценарии завершить, provider отметить NOT_RUN и передать точную потребность; synthetic PASS не выдавать за real-provider PASS.

G10.7-13. Все применимые unit/HTTP/PostgreSQL/frontend/lint/build и browser проходят на едином финальном commit. CI evidence не содержит паролей/state.json/cookies/токенов. В отчёте есть точная ссылка на запуск и SHA, не только локальный текст «всё зелёное».

4. ПРЕДМЕТНАЯ ПРИЁМКА И GC

Отдельно от технической матрицы зафиксировать: утверждены ли применимые admission-правила/предметные ожидания, допущен ли рабочий каталог, просмотрены ли рекомендации экспертом, какие GC имеют требуемые независимые заключения, запускался ли нормативный набор на данной версии механизма. Не заполнять заключения экспертов вместо них и не присваивать approved GC синтетическим fixtures. Reliability остаётся not_verified без требуемого протокола.

Если предметное решение отсутствует, подготовить точный вход для владельца: сценарий, исходные условия, спорное правило, варианты последствий и нужный ответ. Это не повод оставить остальные технические критерии без выполнения.

5. ИТОГ И ПЕРЕДАЧА

Отчёт docs/evc/tasks/task10-7-integrated-product-acceptance.md. Для каждого G10.7-01…13: PASS/FAIL/BLOCKED/NOT_RUN, конкретное доказательство и граница проверки. Отдельные строки: технический путь; real-provider; рабочий каталог; предметный admission; экспертный просмотр; approved GC/нормативная Reliability; текущий CI; состояние развёрнутого test.

Итог не сводить к одному слову PASS. Перечислить, что владелец может принимать сейчас, что блокирует пилот и что является отдельной последующей работой. Указать необходимые решения/доступы без секретов, дефекты с воспроизведением и рекомендуемый порядок устранения. Полная приёмка нового UX/UI выполняется после его реализации отдельным этапом.

Адресные технические ошибки интеграции в области этих задач исправить и проверить самостоятельно. Не устранять провал изменением нормативного результата fixture, отключением защит или удалением негативного сценария. Новый предметный объём/изменение FROZEN не включать скрыто.

ОБЩИЕ УСЛОВИЯ ВЫПОЛНЕНИЯ

Основание: независимая проверка main 8654b97ed6605d560111c37cd291f98f82c41457 от 05.10.2026 после 11.1, 10.2 и 10.3. Отчёт и синтетический скрипт воспроизведения приложены к пакету. Перед работой получить актуальный main, зафиксировать SHA и проверить, не исправлен ли дефект последующими изменениями. Уже исправленное подтвердить проверкой, не переделывать.

Соблюдать AGENTS.md, EVC workflow, verification matrix, artifact recipe и действующие контракты. Применимые источники брать из выбранного source manifest Change 01 и Registry; фиксировать версию и checksum. Не заменять выбранный M1 v1.4 более ранним приложенным M1 v1.2. Наличие FROZEN-документа, технический PASS и нормативная приёмка — разные статусы.

Работать автономно по конкретной задаче. Сначала воспроизвести проблему, затем исправить, добавить необходимые регрессии и проверить реальный путь. Архитектор разрешает обычные технические решения в существующей архитектуре. Не переносить на владельца выбор имён функций, маршрутов и деталей тестов. При действительно отсутствующем предметном решении сформулировать точный вопрос, источник, варианты и влияние; выполнить всю независимую часть, отметить блокировку только зависимой части.

Очистка legacy/MBTI и удаление исторических таблиц/данных НЕ входят в пакет. Новый UX/UI из отдельного чата здесь не внедряется: исправления в текущем интерфейсе. Не менять без отдельной задачи время, правила возврата, формат входа и другие принятые продуктовые нормы. Исправления активных маршрутов допустимы независимо от их старого происхождения.

Не читать и не публиковать секреты или реальные персональные данные. DB-тесты — только на принадлежащей запуску изолированной БД по механизму 10.2. Нельзя использовать рабочий dump или shared test DB вместо воспроизводимого bootstrap. Не ослаблять проверки, не проставлять PASS вручную. Синтетические fixtures не становятся GC и не получают нормативного утверждения.

Опубликованные определения и исторические snapshots/IA/Results/C-67 сохраняются неизменными. Изменения предметных правил и шаблонов выпускать новой версией с источником, checksum и областью применения; GET не запускает скрытую регенерацию. Не пересчитывать историю массово ради нового теста. Если требуется миграция, описать минимальное изменение, совместимость и восстановление; применять её в изолированных тестах, без автоматического вмешательства в рабочую БД.

Результат передать отдельным проверяемым изменением/PR по правилам репозитория. Этот текст поручает реализацию и проверки, но не самостоятельный merge/deploy. Если в текущей сессии владельцем уже дан соответствующий допуск, действовать в его пределах без повторного запроса.

В отчёте: актуальный SHA и diff, источники и решения, изменённые файлы, критерии с PASS/FAIL/BLOCKED/NOT_RUN, команды и фактические результаты, безопасные доказательства, ограничения, откат и зависимости следующей задачи. CI привязать к финальному commit; старый зелёный запуск не приписывать новому дереву. Отсутствие браузера, БД, ключей или эксперта не превращать в PASS. Не объявлять всю систему готовой по одному unit-набору.
