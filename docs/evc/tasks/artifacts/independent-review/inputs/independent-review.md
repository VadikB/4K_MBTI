## Заключение

Доработки действительно присутствуют в main. Исправление оснований рекомендаций,
bootstrap пустой БД, браузерный runner и интеграция CI реализованы. Независимо
пройдены unit, HTTP, frontend и проверки PDF. Сохранённые свидетельства архитектора
подтверждают шесть технических браузерных сценариев с синтетическим AI gateway.

**Полную готовность пользовательского пути M1–M8 подтвердить нельзя.** Обнаружены
четыре конкретные проблемы: доступ к профилю без авторизации, отсутствие обычного
перехода из подтверждения профиля в M4, разрыв истории отчётов и потеря контекста M4
в рекомендациях. Они не требуют очистки legacy-таблиц.

Полный PostgreSQL/browser-прогон в этой среде не состоялся. Это ограничение аудита,
а не доказательство отказа реализации на стенде архитектора. Текущий удалённый CI
и версия развёрнутого test-сервера отдельно не проверены. Реальные данные,
секреты и production/test БД не читались. Изменений кода продукта, merge и deploy нет.

## Что осталось непроверенным независимо

Команда `pytest --run-integration -m integration` выполнена. Результат:
**2 FAIL, 1 PASS, 75 SKIP, 375 deselected**. Два отказа — явные проверки наличия
TEST_DATABASE_URL в clean-bootstrap тестах; остальные DB-тесты пропущены из-за
того же отсутствующего подключения. Никакой DB PASS этому запуску не присваивается.

В среде нет подготовленного PostgreSQL. Подготовка системных пакетов упёрлась
в ограничения смены UID/GID. `npx playwright install chromium` завершился ошибкой
загрузки/распаковки архива. Browser suite независимо **NOT_RUN**; `--list` только
подтвердил наличие шести сценариев и не считается прогоном. Повторять тесты без
их зависимостей бессмысленно; для закрытия нужен изолированный тестовый кластер
и установленный Chromium/Xvfb, например существующий CI архитектора.

В Git есть отчёт архитектора о **78 PostgreSQL PASS и 6 browser PASS**. Эти числа
относятся к его запуску; они не выданы за результат этого аудита. Сохранённый
ci-bd97dc2.json относится к более раннему кандидату bd97dc2, что прямо отмечено
в самом файле. Текущий CI для 8654b97 следует подтвердить отдельно.

## REV-01 — профиль читается и изменяется без авторизации

**Приоритет: блокирующий до пилота с реальными участниками.**

`Api/routes.py:6072`, `get_user_profile_summary`, и `Api/routes.py:6160`,
`update_user_profile`, принимают user_id из URL, не проверяя сессию и владельца.
Router не имеет общей auth dependency. Middleware main.py журналирует запросы,
но не добавляет отсутствующий контроль доступа к этим маршрутам.

На реальном FastAPI router с подменой только SQL-границы синтетическими данными:

- запрос чтения профиля без cookie вернул **200** и синтетический email;
- PATCH профиля без cookie вернул **200** и выполнил один `UPDATE users` в fake connection;
- число обращений к проверке сессии — **0**.

Это воспроизведение логики приложения, не атака на развёрнутый сервер.
Наличие внешней защиты test-сервера не проверялось. Потенциально доступны чтение
профильных данных и изменение email/telegram/avatar выбранного пользователя.
Захват аккаунта данным аудитом не доказывается.

Исправить: требовать действующую сессию и совпадение владельца; отдельный
административный доступ — только через существующую модель прав. Проверить оба
маршрута в состояниях anonymous / owner / другой пользователь / другой tenant.
Нельзя снимать проблему тем, что эти маршруты имеют старое происхождение:
текущий UI продолжает использовать их.

## REV-02 — подтверждение профиля не формирует M4 для нового runtime

**Приоритет: блокирующий для обычного нового участника.**

Обычный `POST /users/agent/profile/confirm` вызывает
`Api/agent.py:3067`, `confirm_existing_profile`. Сохранение профиля в этом пути
идёт в `user_role_profiles` (`Api/agent.py:2603`). Новый старт использует
`Api/m10_product_flow.py:15`, `_owned_profile`, которому нужна ready-запись
в `assessment_personalized_profiles`; при её отсутствии возвращается
`M4_PROFILE_NOT_READY`.

Вызовов `create_personalized_profile` из дерева Api не найдено; функция существует
в `Api/assessment_contexts.py:242`. Это сопоставлено с кодом UI, profile confirm
и места сохранения, а не только с поиском имени. Имеется административный QA-путь
`/admin/m5-lab/migrate-current-profile`, защищённый superadmin и работающий для
самого текущего администратора; он не заменяет обычный путь участника.

В `scripts/test_stand_seed.py` готовые M3/M4 создаются до browser login. Поэтому
зелёный S10-A не проверяет создание M4 из реального пользовательского ввода.
Проверка пустой synthetic M4-выборки воспроизводит `M4_PROFILE_NOT_READY`.
Полная браузерная регистрация нового участника в данном аудите не выполнялась.

Исправить: связать подтверждённые OrganizationContext, выбранную версию M3,
UserContext и конфигурацию оценки со штатным выпуском immutable M4 перед стартом.
Условия недостаточности/конфликтов должны следовать действующим источникам.
Приёмка начинается с участника без готового M4; создавать ему профиль SQL-seed
во время этой проверки нельзя. Организационные и методологические настройки,
подготовленные администратором до прихода участника, допустимы.

## REV-03 — «Мои отчёты» не показывает новые M8 Reports

**Приоритет: блокирующий для завершённого пользовательского пути.**

Dashboard уже считает записи `m8_reports` (`Api/routes.py:601`). Его кнопка
«Перейти к отчётам» вызывает `openReports` (`web/js/screens/dashboard.js:110`).
Но `web/js/screens/profile.js:81` загружает `/users/{id}/profile-summary`, который
строит history только из `user_sessions`/`session_cases`/старых skill assessments.
`web/js/screens/reports.js:60` показывает «Пользователь еще не проходил оценку»
при пустой старой history; открытие и PDF привязаны к legacy session_id.

Контрольный пример: одна новая M8-запись и отсутствие legacy-сессий.
Результат реальных функций на synthetic SQL boundary: dashboard reports_total=1,
profile-summary total_assessments=0. Сохранённый отчёт существует, но текущая
навигация к истории его не обнаруживает. Прямой переход после завершения интервью
к M8 report и reload этого экрана не покрывают данный дефект.

Исправить: owner-scoped список Cycle/Results/Report с корректными ID, переходом
к сохранённой версии и скачиванием PDF. Проверить выход/повторный вход, два Cycle,
revision отчёта и разграничение владельцев. Счётчик должен иметь согласованную
семантику: сейчас он считает все Report revisions как отдельные отчёты.
Старую историю можно сохранить отдельно без удаления таблиц и данных.

## REV-04 — рекомендации теряют существующий контекст M4

**Приоритет: существенный дефект персонализации.**

`Api/m8_recommendations.py:14` и `profile_projection` читают, например,
`role_profile.mission`, `role_profile.typical_tasks`, `user_context.position`.
Фактическая M4-структура содержит `role_profile.card.mission`,
`role_profile.card.typical_tasks`, `user_context.position_or_status` и
`organization_context.activity_description`.

На сохранённом synthetic Results из scenario-1 все четыре соответствующих поля
присутствуют, но реальный `profile_projection` возвращает **{}**. Все четыре
рекомендации положительного примера получают сообщение об отсутствии контекста.
Это уже видно в сохранённых JSON/PDF архитектора; отсутствие контекста не вызвано
тем, что участник не заполнил профиль.

Исправить: согласовать явную безопасную проекцию с канонической M4-схемой.
Не расширять её слепым копированием identity/contact-полей. Тест должен строить
M4 штатным builder и проводить его до Results/C-67/PDF, а не использовать
упрощённый вручную выдуманный профиль. Исторический Results не переписывать;
обновление представления проводить через предусмотренную Report revision.

## Что исправлено и что ещё ограничивает выводы

1. **Первоначальный дефект рекомендаций исправлен в проверенной области.**
   IE и пустые/недопустимые основания не выбираются как подтверждённое проявление.
   Есть server-side resolver Results → C-56 → IA → Evidence → материал, проверки
   ссылок и hashes. Старые непроверенные рекомендации скрываются при выдаче без
   изменения сохранённой истории; generation failure отделён от нехватки оснований.
   Соответствующие unit-тесты прошли; новый независимый DB-прогон остаётся открыт.

2. **Типы рекомендаций больше не выдаются всем автоматически.**
   Однако Consolidation/Transfer покрывают только два явно описанных действия
   K1.I01 и K1.I13. Для остальных допустимых результатов реализован Development.
   Это раскрыто в отчёте 11.1 и не является полным содержательным покрытием всей M2.
   Расширение требует предметного просмотра, не механического добавления трёх типов.

3. **Ошибка схемы created_at/frozen_at исправлена.** `_owned_profile` теперь
   сортирует по frozen_at. Bootstrap и два независимых empty-DB прогона реализованы
   как реальные entrypoints; все DB PASS пока подтверждены отчётом автора, а не
   повторным запуском здесь.

4. **Admission 8.1 остаётся отдельной незакрытой задачей.**
   `Api/m6_admission.py:43` сохраняет из контекста только AS id, base_role и case_ref.
   Различия полномочий, доступных материалов и влияния уточнений содержательно не
   проверяются. На synthetic примере с одинаковой ролью и разными полномочиями/
   материалами numeric_admissible=true. Это доказывает отсутствие соответствующей
   проверки, но не устанавливает, что любые разные ситуации надо отклонять.
   Нужны явные предметные правила и проверка их реализации.

5. **Пользовательский допуск кейсов не доказан этими тестами.**
   Пять исходных кейсов в Git имеют WORKING; CASE-TDISC-04 содержит открытое решение
   по ветви Аси. Тестовый seed меняет выбранные копии и добавляет synthetic QA PASS
   только в одноразовую БД. Это корректно для проверки механики, но не подтверждает
   наличие разрешённого рабочего каталога на развёрнутом стенде. Его фактическое
   состояние следует проверить отдельно; нельзя автоматически присвоить FROZEN.

6. **GC/реальный provider не проверены.** Нет основания менять Reliability
   с not_verified. Синтетический gateway не измеряет качество извлечения и оценки
   реальных ответов. Реальный provider smoke и экспертные GC остаются отдельными
   воротами приёмки.

7. **Небольшое замечание к свидетельству candidate.json.** Из 74 перечисленных
   файлов 56 совпадают с main; 18 старых имён web/dist отсутствуют. Все перечисленные
   исходники, текущий web/dist/main.js и sources.json совпадают, build воспроизводится.
   Следовательно, нельзя назвать весь manifest точным снимком текущего дерева,
   но и нельзя из этого заключить, что исходники браузерных тестов не совпадают.
   Стоит переснять manifest и приложить текущие CI checks для финального SHA.
