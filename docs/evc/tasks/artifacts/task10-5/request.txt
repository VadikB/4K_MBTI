ЗАДАНИЕ 10.5 — ШТАТНЫЙ ПЕРЕХОД ОТ ПРОФИЛЯ УЧАСТНИКА К M4 И СТАРТУ ОЦЕНКИ
Редакция 1. Дата: 05.10.2026. Зависимость: 10.4. Адресат: архитектор → Codex.

1. РЕЗУЛЬТАТ

Допущенный обычный участник без готового PersonalizedProfile проходит существующие экраны контекста/профиля, подтверждает данные и получает пригодный для нового runtime immutable M4. Оценка стартует с этим snapshot без SQL-подготовки профиля, superadmin-операций или лабораторной миграции пользователя.

2. ОСНОВАНИЕ

REV-02: Api/agent.py::confirm_existing_profile сохраняет старый user_role_profiles; Api/m10_product_flow.py::_owned_profile требует ready assessment_personalized_profiles. Штатный вызов create_personalized_profile из Api не найден. scripts/test_stand_seed.py заранее создаёт M3/M4, поэтому прежняя браузерная приёмка не проверяет этот переход. Отсутствие M4 даёт M4_PROFILE_NOT_READY.

Применимые источники: выбранные M3.RoleProfile/BaseRoles, M4.Context, M1, M5 и ADR 002; контракт build_personalized_profile/create_personalized_profile, published configuration и источники контекста. Ответственность: подготовка входа PM-03 и его стык с M5/M7. Норму достаточности контекста не заменять произвольным числом заполненных полей.

3. РЕАЛИЗАЦИЯ

— Проследить текущую цепочку: допуск/активная организация → выбор опубликованного M3 → подтверждённый UserContext → опубликованный OrganizationContext → конфигурация оценки → M4 → Cycle. Указать отсутствующие вызовы/контракты и связать их в основной пользовательский путь.
— Администратор вправе заранее настроить организацию, версионированные роли, контекст организации, методологию и назначения. Сам пользовательский M4 создаётся штатным механизмом после требуемого подтверждения; test seed не заменяет этот шаг.
— Текущее отображение роли/должности допускается связать с новой моделью через ограниченный явный адаптер. Не считать совпадение старого numeric role_id и нового version_id доказательством соответствия; не выбирать роль по первому элементу/максимальному ID.
— Проверять владельца, активную организацию, доступность роли, конфигурацию, подтверждённость исходников, checksum и предусмотренные конфликты. Если активная область неоднозначна — явное состояние выбора/неготовности, не случайный профиль.
— Сформировать M4 через существующий canonical builder/repository. Сохранить версии, provenance, checksum и применимые ограничения. Не копировать контакты/identity в runtime-контент.
— Ready означает выполнение действующих контрактов. При недостаточных/конфликтующих данных показать конкретный исправимый шаг. Состояние blocked не превращать в ready ради старта.
— Двойной submit, reload, потеря HTTP-ответа и повторное подтверждение одинакового ввода не создают конфликтующих профилей/циклов. Частичный сбой не оставляет ложное ready. Повтор безопасен.
— Новое подтверждение изменённых исходных данных создаёт новую версию/новый snapshot по контракту. Уже начатый Cycle продолжает использовать собственный профиль; старые AS/Results/Report не меняются. Новый Cycle выбирает профиль в правильной организации/конфигурации, а не просто последнюю ready-запись user_id.
— Кнопки заполнения профиля, подтверждения и старта ведут к нужному состоянию, без циклического возврата «заполните профиль» после успешного подтверждения.
— Развести «профиль готов» и «есть допустимый маршрут/каталог кейсов». Отсутствие допущенных кейсов не выдавать за ошибку M4; показать причину и административное действие, без скрытого допуска WORKING-кейсов.

4. ПРИЁМКА

P10.5-01: на свежем стенде создан обычный допущенный аккаунт, но отсутствуют его UserContext/M4 и результаты. Данные участника вводятся/подтверждаются через UI и штатные API; после этого M4 ready сохранён с верными refs/checksum.
P10.5-02: browser стартует Cycle и получает первую AS, связаны owner/organization/M3/M4/configuration. После начала и во время теста M4 SQL-вставками не создаётся.
P10.5-03: для синтетического технического маршрута разрешён отдельно обозначенный case fixture; он не маскирует статус рабочего каталога и не является GC.
P10.5-04: неподтверждённый контекст, чужая роль/организация, блокирующий конфликт и отсутствующий обязательный источник не дают ошибочного ready; UI объясняет дальнейшее действие.
P10.5-05: повторное подтверждение/reload/сбой между шагами не создают дубли или ложное состояние; изменения сохраняются согласованно.
P10.5-06: изменение профиля после старта не меняет snapshot открытого/закрытого Cycle. Следующий независимый Cycle использует допустимый новый профиль.
P10.5-07: чужой профиль и прежняя организация не подхватываются как вход новой оценки. Историческое чтение работает в пределах существующих прав.
P10.5-08: ready M4 без допустимых кейсов даёт отдельное состояние отсутствия маршрута. Не создаются фиктивные Turns/IA/Report и ложная завершённая оценка.
P10.5-09: сборка на пустой БД 10.2 и действующий browser suite 10.3 сохраняют работоспособность; применимые регрессии и CI пройдены.

5. ПЕРЕДАЧА

Отчёт docs/evc/tasks/task10-5-user-profile-to-m4.md: схема вызовов, сопоставление полей старой формы с каноническими M3/M4, состояния, refs одного синтетического прохождения, подтверждение отсутствия готового M4 перед UI и ссылка на browser evidence. Отдельно указать фактическую готовность рабочего каталога; не закрывать её техническим seed.

ОБЩИЕ УСЛОВИЯ ВЫПОЛНЕНИЯ

Основание: независимая проверка main 8654b97ed6605d560111c37cd291f98f82c41457 от 05.10.2026 после 11.1, 10.2 и 10.3. Отчёт и синтетический скрипт воспроизведения приложены к пакету. Перед работой получить актуальный main, зафиксировать SHA и проверить, не исправлен ли дефект последующими изменениями. Уже исправленное подтвердить проверкой, не переделывать.

Соблюдать AGENTS.md, EVC workflow, verification matrix, artifact recipe и действующие контракты. Применимые источники брать из выбранного source manifest Change 01 и Registry; фиксировать версию и checksum. Не заменять выбранный M1 v1.4 более ранним приложенным M1 v1.2. Наличие FROZEN-документа, технический PASS и нормативная приёмка — разные статусы.

Работать автономно по конкретной задаче. Сначала воспроизвести проблему, затем исправить, добавить необходимые регрессии и проверить реальный путь. Архитектор разрешает обычные технические решения в существующей архитектуре. Не переносить на владельца выбор имён функций, маршрутов и деталей тестов. При действительно отсутствующем предметном решении сформулировать точный вопрос, источник, варианты и влияние; выполнить всю независимую часть, отметить блокировку только зависимой части.

Очистка legacy/MBTI и удаление исторических таблиц/данных НЕ входят в пакет. Новый UX/UI из отдельного чата здесь не внедряется: исправления в текущем интерфейсе. Не менять без отдельной задачи время, правила возврата, формат входа и другие принятые продуктовые нормы. Исправления активных маршрутов допустимы независимо от их старого происхождения.

Не читать и не публиковать секреты или реальные персональные данные. DB-тесты — только на принадлежащей запуску изолированной БД по механизму 10.2. Нельзя использовать рабочий dump или shared test DB вместо воспроизводимого bootstrap. Не ослаблять проверки, не проставлять PASS вручную. Синтетические fixtures не становятся GC и не получают нормативного утверждения.

Опубликованные определения и исторические snapshots/IA/Results/C-67 сохраняются неизменными. Изменения предметных правил и шаблонов выпускать новой версией с источником, checksum и областью применения; GET не запускает скрытую регенерацию. Не пересчитывать историю массово ради нового теста. Если требуется миграция, описать минимальное изменение, совместимость и восстановление; применять её в изолированных тестах, без автоматического вмешательства в рабочую БД.

Результат передать отдельным проверяемым изменением/PR по правилам репозитория. Этот текст поручает реализацию и проверки, но не самостоятельный merge/deploy. Если в текущей сессии владельцем уже дан соответствующий допуск, действовать в его пределах без повторного запроса.

В отчёте: актуальный SHA и diff, источники и решения, изменённые файлы, критерии с PASS/FAIL/BLOCKED/NOT_RUN, команды и фактические результаты, безопасные доказательства, ограничения, откат и зависимости следующей задачи. CI привязать к финальному commit; старый зелёный запуск не приписывать новому дереву. Отсутствие браузера, БД, ключей или эксперта не превращать в PASS. Не объявлять всю систему готовой по одному unit-набору.
