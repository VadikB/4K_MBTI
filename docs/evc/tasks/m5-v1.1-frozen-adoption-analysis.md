# Анализ внедрения M5 v1.1 FROZEN

Дата анализа: 01.10.2026. Статус задачи: анализ завершён; зависимая реализация
продолжается по Change 01: технические контракты и fixtures разрешены сейчас;
обновлённый пул Case требуется для содержательной приёмки.

## Результат

Определён переход от действующего лабораторного контракта M5 по комплекту
v0.4 WORKING к M5 v1.1 FROZEN / CURRENT=NO. Предложена реализация, в которой
версия Case хранит точные `IndicatorIDs` и версию M2, персонализация сохраняет
этот перечень, а Assessment Situation конкретизирует и проверяет условия
наблюдения каждого IndicatorID. Подбор, последовательность, покрытие конструкта
и бюджет сессии остаются ответственностью M7.

Этот анализ не публикует M5 как CURRENT, не изменяет runtime, схему БД или
существующие данные и не присваивает FROZEN действующему WORKING-пулу.

## Область

- Включено: методология и паспорт M5 v1.1; влияние на файловый контракт,
  артефакты Case/AS, БД, Prompt Lab, границы M4/M6/M7, QA и test-контур.
- Не входит: переатрибуция существующих Case, разработка алгоритма M7,
  оценивание M6, публикация CURRENT по M0, миграция сохранённых сессий и deploy.

### Ограничения первоначального анализа (история, не текущие общие блокеры)

1. В репозитории нет зарегистрированного исходного пакета M5 v1.1 и процедуры
   его публикации по M0. DOCX имеет статус FROZEN, но CURRENT=NO.
2. В комплекте нет новых версий конкретных Case с полем 22 `IndicatorIDs`,
   версиями M2 и проверенными условиями для каждой роли/AS. Документы прямо
   запрещают автоматически переносить старый пул.
3. Текущий `CaseDefinition` содержит 21 поле. `IndicatorIDs` появляются лишь
   через candidate Observability и AS, что противоречит M5 v1.1 и M1 v1.4.
4. Из 80 записей candidate Observability старого пула 14 K2-записей имеют
   `pending_methodological_review`; они не могут стать точными целями Case
   техническим преобразованием.
5. M5 v1.1 построен с учётом M6 v1.7 REVIEW. M1 v1.4 сообщает о M6 v1.8 FROZEN,
   но применимый источник M6 v1.8 в Registry не проверен и в репозитории
   отсутствует. Перед runtime-интеграцией M5→M6 нужен impact review.
6. M1 v1.4 сообщает о M7 v1.3 FROZEN, но источник и задача M7 в Registry не
   внесены. Поэтому контракт передачи каталога можно подготовить, а алгоритм
   выбора/закрытия/уточнений M7 в рамках M5 определять нельзя.

## Изменение контракта

| Область | Сейчас | Требование M5 v1.1 | Предлагаемое изменение |
| --- | --- | --- | --- |
| Паспорт Case | 21 поле | 22 поля | Добавить `indicator_targets` как список точных `IndicatorID`, версии M2, связи с Applicability и проектных условий |
| Владение целями | Кандидаты около AS | CaseVersion | Запретить добавление/удаление целей персонализацией и ответами |
| AS | Список Observability содержит цели | Сохраняет цели Case и конкретизирует условия | Проверять полное равенство множества целей CaseVersion и AS; для каждой цели сохранять условия/ветви/QA |
| Версионирование | Ссылки/checksum частично есть | Изменение цели создаёт новый Case | Неизменяемая CaseVersion и snapshot в AS/session; исторические снимки не переписывать |
| Ветви | Текстовый Dialogue | Восстановимы предусмотренное и фактическое событие | Ввести технические записи branch/event в трассе, не создавая новой методологической сущности |
| Завершение | Недостаточно разделено | Scenario, AS, Dialogue, pause и Cycle различны | Раздельные состояния и события; переходы M7/M6 — после проверки их контрактов |
| QA | Лабораторные NOT_RUN | Протокол по CaseVersion/role/AS/trajectory/Indicator | Сохранять run, вход, трассу, условия каждой цели, время, результат, дефект и retest |

Название `indicator_targets` предлагается для машинного контракта, чтобы рядом
с ID хранить версию M2 и проектные условия. Нормативное поле паспорта остаётся
`IndicatorIDs`. Окончательное имя публичного JSON/API и схема БД требуют решения
технического владельца до реализации.

## Предлагаемый план реализации

Каждый этап ниже — отдельный независимо принимаемый результат/PR.

### 1. Зафиксировать источник и Change & Impact

- Сохранить исходные DOCX неизменяемыми в согласованном контуре Sources с
  указанными checksum; добавить запись M5 v1.1 FROZEN / CURRENT=NO в Registry.
- Зафиксировать зависимости M6 v1.7/v1.8 и M7 v1.3 как открытые; не переключать
  CURRENT и runtime.
- Не заменять каталог `cases/competencies_4k/1.1`, пока его version namespace
  не разведен со старым draft-пакетом.

Результат: воспроизводимый источник и формально видимое влияние без изменения
поведения системы. Требуется решение владельца выпуска о целевом пути Sources.

### 2. Ввести совместимый контракт Case v2

- Создать новую schema version, не переписывая сохранённый v1/21-field формат.
- Хранить `CaseTypeIDs` как 1..N и `IndicatorIDs` как независимое 1..N отношение.
- Для каждой цели валидировать существование и принадлежность Skill/Component
  в точной версии M2; не выводить цели из CaseType или Applicability.
- Валидировать уникальность ID, наличие условий наблюдения, роли и инвариант.
- Конвертацию старого Case разрешать только при явной атрибуции всех целей;
  иначе результат остаётся WORKING/непригодным для runtime.

Результат: файловая схема и loader принимают новый Case, а старые снимки читаются
по прежней версии. Никакие предметные ID не зашиваются в Python/JS.

### 3. Согласовать и реализовать хранение

- Использовать существующие `case_registry_indicators` и
  `session_case_indicators` как основу после проверки связи с неизменяемой
  CaseVersion. Если `cases_registry_id` не представляет версию, добавить
  версионную сущность/ключ, не меняя смысл старых строк.
- Сохранять ссылку на M2 methodology version, порядок, обязательность и checksum
  полного Case artifact. Не хранить один скалярный `type_code` как источник целей.
- При создании AS копировать полный набор целей CaseVersion в snapshot одной
  транзакцией; отказ при пустом, частичном или неизвестном наборе.
- Миграцию существующих строк не выполнять до утверждённой таблицы соответствия;
  старые сессии продолжают читать прежние snapshots.

Результат: по идентификатору AS восстанавливается CaseVersion → M2 version →
полный набор IndicatorIDs. Требуются согласованные совместимость и откат схемы.

### 4. Обновить генерацию Assessment Situation

- Вход: выбранная M7 версия Case, зафиксированный PersonalizedProfile M4,
  одна допустимая BaseRole и разрешённый контекст.
- Персонализация меняет только разрешённые слоты и ролевую реализацию; сохраняет
  CT-композицию, задачу, полномочия, Applicability и точные IndicatorIDs.
- До первого Turn проверять инвариант и условия каждой цели. Потеря обязательного
  условия даёт AS `FAIL/not_ready` и допускает повторную персонализацию; список
  целей не сокращается. После первого Turn AS не регенерируется и не заменяется.
- Фиксировать исходные материалы, substitutions с происхождением/checksum,
  ветви и их условия, плановое время и QA snapshot.

Результат: воспроизводимая AS, полностью совпадающая по целям с CaseVersion.

### 5. Обновить Prompt Lab как проверочный адаптер

- Добавить явный выбор версии нового Case и синтетического PersonalizedProfile
  для минимум двух допустимых BaseRole.
- Перед LLM сохранять проверенный input snapshot; после генерации — output,
  проверку инварианта, цель-за-целью Observability и итог AS readiness.
- Показывать в UI и API `CaseID/version`, BaseRole, M2 version, IndicatorIDs,
  условия и PASS/FAIL/NOT_RUN. ID не включать в предъявляемый оцениваемому текст.
- Сохранить детерминированный режим без LLM; реальные вызовы оставить отдельным
  `llm`-прогоном. Prompt — новый versioned artifact, а не строка в коде.

Результат: на test вручную и автоматически создаются AS для разных ролей, а
сохранённые артефакты можно повторно прочитать и сверить.

### 6. Подготовить handoff без реализации M6/M7

- Каталог для M7 отдаёт только прошедшие QA CaseVersion: роли, Applicability,
  точные IndicatorIDs/M2 version, planned time, ограничения и readiness.
- Материал M6 содержит AS/Case refs, полный неизменный список целей, профиль,
  роль, исходные материалы, фактические Turns/events, время и раздельные статусы
  scenario/AS/Dialogue. Не создавать EB/IA и не вычислять L0 в M5.
- Технические потребители проверяются fixtures/stubs до общего прогона; подробные
  алгоритмы M6/M7 сверяются адресно по исходникам перед их реализацией.

  алгоритмов; нормы стыков из Change 01 доступны сейчас.

  участок. CURRENT и массовая миграция не входят в задачу.

## Критерии приёмки реализации

- [ ] Case v2 содержит 1..N точных IndicatorIDs одной или явно заданных версий
  M2; каждый ID принадлежит заявленной Applicability.
- [ ] Один Case с одним или несколькими CaseType поддерживает несколько Indicators;
  `type_code` не ограничивает связь.
- [ ] AS сохраняет полный набор CaseVersion; персонализация, LLM и ответы не могут
  добавить или удалить цель.
- [ ] Потеря обязательного условия до старта блокирует readiness всей AS, сохраняя
  причину по конкретной цели; отсутствие проявления после старта не становится L0.
- [ ] Старые Case/sessions продолжают читаться без молчаливой переатрибуции.
- [ ] На test минимум две ролевые генерации создают доступные для просмотра записи:
  input snapshot, output, проверки, `CaseID/version`, M2 version, IndicatorIDs,
  условия Observability и итог.
- [ ] Автоматическая проверка повторно читает эти записи и сверяет checksum,
  полноту целей и ролевой инвариант.
- [ ] M5 не выбирает следующий Case, не считает покрытие/бюджет и не создаёт
  Evidence/EB/IA.
- [ ] Новый предметный текст и значения находятся в versioned artifacts, а не
  встроены в генератор.

## План проверки

- Contract/unit: Case v1 compatibility; Case v2 schema; 1..N CT; 1..N Indicators;
  принадлежность M2; запрет дубликатов/неизвестных целей; equality Case↔AS;
  partial Observability; неизменность snapshot; запрет регенерации после Turn.
- Artifact: format, source hashes, manifest, ссылки, deterministic read-back и
  отсутствие fallback на встроенный Case/prompt.
- DB integration на изолированной БД с `test`/`pytest` в имени: versioned mapping,
  атомарный freeze, read-back, legacy rows и rollback expand-схемы.
- HTTP/e2e: детерминированные генерации двух ролей, сохранение/получение артефактов,
  отказ для неподходящей роли и AS с потерянной обязательной целью.
- LLM: stub gateway в стандартном наборе; реальный gateway только с marker `llm`.
- Test stand: зафиксировать deployed commit/version, два run ID, ссылки/запросы
  просмотра и результаты автоматической сверки. Использовать синтетические данные.
- Перед PR: локальный минимум `git diff --check`, backend, HTTP и integration
  согласно `docs/evc/verification-matrix.md`; обязательный CI перед слиянием.

## Откат

- До переключения runtime: удалить только новую регистрацию/draft, сохранив
  неизменяемые источники и отчёт анализа.
- После добавления схемы: expand-only таблицы/колонки; отключить новый loader и
  генерацию feature/config switch, вернуть чтение v1. Новые snapshots сохранять
  для аудита; физическое удаление — отдельная согласованная миграция.
- После test deploy: развернуть предыдущий проверенный commit; новые лабораторные
  runs остаются помеченными версией и не используются в оценке.
