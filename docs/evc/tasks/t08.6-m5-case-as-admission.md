`AS_NOT_ADMITTED`; старый несовместимый Case не подставляется.

## Целевой контракт

### Package и CaseVersion

- `normative_m5_ref`: ID, version `1.1`, status и checksum источников.
- `package_schema_version: 2` и собственный `package_version`; эти версии не
  совпадают автоматически с M5, CaseVersion или AS schema version.
- Неизменяемая CaseVersion содержит все 22 смысловых поля паспорта.
- `case_type_ids: 1..N` и отдельная `ct_composition_logic`.
- `applicability: 1..N` пар SkillID/ComponentID.
- `indicator_targets: 1..N`, где каждая цель содержит:
  `indicator_id`, точный `m2_ref`, SkillID/ComponentID, обязательность,
  проектные условия, scenario locations/branches, event condition,
  observable form и loss risk.
- `applicable_base_roles: 1..N`; для каждой заявленной роли присутствует
  проверяемая role branch и границы полномочий.
- Content checksum включает весь канонический CaseVersion; изменение любой цели,
  центральной задачи или ветви создаёт новую версию.

Валидатор разрешает Indicator только когда C-1X находит точную M2 version и
подтверждает соответствие Skill/Component. Он не наследует все Indicators
Component, не выводит цели из CaseType и не принимает candidate hypotheses.

### AssessmentSituation и C-34

AS snapshot содержит ссылки/checksum CaseVersion, ProfileSnapshot, M2 refs и
правила персонализации; одну BaseRole; substitutions с происхождением; исходное
предъявление и материалы; сценарий и условия ветвей; planned time; точную копию
всех indicator targets с конкретизированными условиями; admission evidence.

Инварианты admission:

- множество пар `(IndicatorID, M2 ref)` в AS строго равно CaseVersion;
- роль входит в CaseVersion и совпадает с frozen profile/мандатом;
- CT-композиция, центральная задача, информационная структура и Applicability
  сохранены;
- каждое обязательное условие технически доступно до первого Turn;
- `format_validation`, `case_qa` и `as_validation` имеют PASS для точной версии,
  роли и scope; FAIL/NOT_RUN не дают допуска;
- fixture/stub evidence маркирован `synthetic` и никогда не удовлетворяет
  пользовательскому admission policy.

После первого Turn snapshot не регенерируется. Ненаступившая корректно
предусмотренная ветвь фиксируется событием runtime и не изменяет исходные цели.

### Граница XLSX, артефактов и кода

XLSX с разрабатываемыми Cases является редактируемым authoring master. Его можно
изменять в ходе командной работы без фиксации каждого промежуточного сохранения.
Перед воспроизводимой проверкой, QA или импортом создаётся source snapshot с
редакцией, checksum и датой. Именно snapshot, собранный package, CaseVersion и AS
неизменяемы после использования; рабочий XLSX не замораживается.

В Python/JS остаются только технические механизмы: чтение формата, применение
JSON Schema, разрешение versioned refs, проверка ключей/иерархий/полного равенства
target set, canonical checksum, транзакции, идемпотентность и безопасные ошибки.
Содержание 22 полей, CaseType/Role/Indicator targets, сценарии, условия наблюдения,
QA-траектории и состав evidence допуска хранятся в versioned artifacts.

Номер CaseVersion задаёт владелец артефакта. Валидатор не назначает версию и не
исправляет содержание; он отклоняет изменённый canonical Case под уже известной
парой CaseID/CaseVersion. Перечень обязательных evidence и допустимые результаты
задаёт versioned admission-policy artifact. Код выполняет эту политику как общий
движок, не содержит M5-список проверок в условных ветвях.

## Хранение и совместимость

Текущие `cases_registry` и `case_type_passports` имеют один FK Case→CaseType,
уникальный `case_id_code` и изменяемое поле `version`; этого недостаточно для
immutable multi-CT CaseVersion. `case_registry_indicators` не хранит условия,
ветви и checksum цели. Поэтому не перегружать эти таблицы новым смыслом.

Сначала сопоставить требования с существующим storage и принятыми объектами задания
4. Не создавать отдельную БД или параллельный каталог только ради карантина.
Если необходимых immutable refs/materials/rules/evidence нет, предусмотреть
expand-only записи нового контура:

- `m5_packages` и `m5_package_imports` — artifact identity, checksum,
  состояние verify/load/activation и причина ошибки;
- `m5_case_versions` — immutable content/snapshot refs и статус lifecycle;
- `m5_case_version_types`, `m5_case_version_roles`,
  `m5_case_version_applicability`, `m5_case_version_targets`;
- `m5_case_qa_runs` и evidence refs;
- `assessment_situation_snapshots`, `assessment_situation_targets`,
  `assessment_situation_qa_runs`;
- activation pointer для нового opt-in пути, меняемый атомарно только после
  успешной загрузки всего пакета.

Физический DDL уточняется в миграционном шаге после карты потребителей. Старые
таблицы и snapshots не переписываются; чтение legacy сохраняется своим адаптером.

## План реализации

Каждый этап завершается самостоятельно проверяемым результатом и оформляется
отдельным PR. Несвязанный рефакторинг в эти PR не включается.

### PR 1 — Source/contract package v2

1. Зарегистрировать постановку T08.6 и ссылку на этот план; не менять FROZEN-файлы.
2. Создать schema-2 package manifest и JSON Schemas как единственный текущий
   контракт M5. Pydantic-модели являются только техническим отражением
   схемы и не содержат предметных значений или собственной нормы.
3. Перенести 22 смысловых поля в схему; предметные значения fixture хранить в
   versioned test artifact, не в Python/JS.
4. Расширить `build_m5_case_package.py`: source refs, независимые версии,
   canonical checksums, C-1X validation, exact target set и role branch checks.
5. Удалить старый v0.4 пакет из актуального дерева; его история остаётся в Git.

Приёмка: contract tests; unknown M2/version, hierarchy mismatch, duplicate,
empty targets, role mismatch и потеря одного target отклоняются.

### PR 2 — QA evidence и versioned admission policy

1. Ввести типизированные evidence `format_validation`, `case_qa`, `as_validation`
   с PASS/FAIL/NOT_RUN, validator version, scope, source refs, trace/defect/owner.
2. Создать versioned admission-policy artifact с требуемыми типами evidence,
   результатами и scope. Реализовать общий policy evaluator C-34; убрать
   возможность считать один boolean достаточным основанием.
3. Развести synthetic и user-eligible scope на уровне типа/политики.
4. Добавить безопасные причины `SOURCE_UNRESOLVED`, `TARGET_SET_MISMATCH`,
   `ROLE_NOT_ALLOWED`, `AS_NOT_ADMITTED`, `CHECKSUM_MISMATCH`.

Приёмка: структурный PASS без Case QA/AS QA не допускает AS; NOT_RUN не PASS;
fixture с искусственными PASS остаётся недоступной пользовательскому пути.

### PR 3 — Expand storage и управляемый loader

1. Зафиксировать карту legacy/new данных и SQL expand-миграцию.
2. Реализовать offline `--verify-only` без записи и отдельный `--apply` только
   для изолированной БД; не подключать импортёр к БД в dry-run.
3. Загружать пакет и CaseVersion в транзакции, проверять checksum и conflicts.
4. Повтор того же artifact id/checksum идемпотентен; тот же id с иным checksum
   отклоняется; ошибка любого Case не создаёт частично активный пакет.
5. Activation pointer обновляется отдельной атомарной операцией после load.

Приёмка: DB integration подтверждает verify/load/activate как разные состояния,
повторный импорт, rollback транзакции, сохранение старых ссылок и отсутствие
частичной активации.

### PR 4 — AS builder из frozen PersonalizedProfile

1. Принимать C-23/ProfileSnapshot T08.5 по ID/version/checksum; не читать заново
   текущий `active_profile_id` после начала Cycle.
2. Строить AS только из выбранной CaseVersion и одной разрешённой роли.
3. Сохранять substitutions, материалы, presentation и конкретные условия каждой
   цели до вызова генератора; LLM получает минимальную разрешённую проекцию без PII.
4. После генерации проверять инвариант и строгое равенство target set.
5. При потере условия возвращать AS not ready и разрешать пересоздание только до
   первого Turn. Не удалять проблемную цель.

Приёмка: T03/T04 unit и DB tests; изменение Case/Profile после создания не меняет
snapshot; потеря одного из нескольких targets откатывает создание целиком.

### PR 5 — основной runtime gate и C-34 handoff

1. Добавить отдельный opt-in режим новой оценки; legacy остаётся на своём пути.
2. Все точки предъявления нового режима получают AS только через admission policy.
3. Передать C-34 snapshot ref, цели, материалы, условия и evidence refs исполнителю.
4. При отсутствии допустимого Case вернуть «Оценка ещё не готова к запуску» и
   сохранить техническую причину/correlation ID; fallback на legacy запрещён.
5. Не реализовывать выбор следующего Case: runtime принимает выбор/AS от M7/stub.

Приёмка: HTTP/e2e доказывает admitted path, отказ по роли/целям/QA, отсутствие
fallback и неизменность предъявления после изменения активных артефактов.

### PR 6 — Prompt Lab и test-доказательства

1. Перевести лабораторию на schema-2 fixture и настоящий AS builder, сохранив
   `synthetic=true`, `admitted_for_assessment=false` для пользовательского scope.
2. Показывать package/Case/AS/Profile refs, exact targets, условия, три слоя QA,
   checksums и причины отказа; IndicatorIDs не включать в текст для оцениваемого.
3. Сохранять input/output/verification trace и обеспечивать read-back по run ID.
4. Развернуть на test тот же commit, который прошёл CI; выполнить минимум две
   синтетические роли и автоматический негативный сценарий.

Приёмка: пользователь видит артефакты в Prompt Lab/диагностическом API; DB read-back
совпадает с показанными refs/checksums; техническая fixture не появляется в пуле.

### Этап после получения новых Cases

1. Зарегистрировать нормативный CT01–CT20 v1.0 и новые Case как отдельные версии.
2. Выполнить Case QA для конструкции, каждой роли и сценарных траекторий M5.6.
3. Выполнить AS QA на разрешённых профилях и эмпирический пилот; сохранить trace.
4. Активировать только версии с полным evidence точного scope.
5. Проверить handoff с M7/M6 по предоставленным оригиналам; fixture/старый пул
   не использовать как содержательное доказательство.

## Проверки

- HTTP/e2e: C-23→AS builder→C-34→presentation; все отрицательные admission cases;

- LLM: stub gateway в стандартном наборе; реальный вызов только marker `llm`.
- Test: deployed commit/version, package/import/AS/run IDs, две роли, негативный

- Перед каждым PR — применимый локальный минимум verification matrix; перед
  слиянием — обязательный CI и review человека-владельца.

## Откат

- Package/loader: не активировать новый package; прежний пакет и refs неизменны.
- Storage: expand-таблицы остаются для чтения/аудита; запись нового режима
  отключается, удаления и backfill нет.
- Runtime: выключить opt-in/activation pointer и вернуть предыдущий проверенный
  commit; уже созданные AS остаются читаемыми, новые Turns в них не принимаются
  без совместимого runtime.
- Test deploy: штатный rollback на предыдущий commit; лабораторные runs сохраняются
  с версией и synthetic marker.
