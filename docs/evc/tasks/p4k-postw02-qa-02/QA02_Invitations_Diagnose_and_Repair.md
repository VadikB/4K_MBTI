# P4K-POSTW02-QA-02 — внедрить состояния приглашений и явные причины отказа

Редакция 1.1 · 17.11.2026. Статус: реализация утверждённой владельцем матрицы состояний и причин приглашений. Заменяет ограниченный объём редакции 1.0. Диагностика массового отказа TEST вынесена в отдельный QA-05 и выполняется первой в режиме read-only.

## Результат

Полностью реализовать `Invitation_Behaviors_Draft.md` редакции 1.1: общий серверный контракт, клиентское представление, восстановление прежней попытки, частичные batch, отдельные сведения о письме, ссылке и регистрации. Администратор и суперадминистратор видят конкретную безопасную причину подтверждённого отказа и доступное действие. Неопределённый исход не превращается в ложное «не отправлено» или повторную рассылку. Подтверждённый отказ неизвестной безопасной категории остаётся отказом. Допустимую отправку через обе роли проверить управляемым transport.

## Что подтверждено

Владелец сообщает об отказе у обеих ролей. Обе используют POST `/users/admin/organizations/{organization_id}/personal-invitations` и общий почтовый транспорт. В `web/js/screens/admin/organizations.js:87–105` formatter игнорирует `items[].error`: причины «анкета», «не настроен сервис», «отказ провайдера» и «участник недоступен» дают одинаковый совет проверить адрес/почту. Это воспроизведённый дефект. Какая из причин действует на TEST, пока неизвестно.

Слой: административный UI → invitation API/ACL/readback → почтовый адаптер. Готовность назначения — потребитель сведений PM-02; эта карточка не перерабатывает анкету или методологию.

## Выполнить

1. Использовать отчёт первого read-only задания QA-05 как вход о живом серверном состоянии. QA-02 не выполняет повторную серверную ревизию и не меняет environment/ключи/настройки TEST автоматически. Если выявлена отдельная конфигурационная причина, указать её как внешний остаток для адресного решения; реализацию согласованных состояний продолжить. Причину живого отказа не выводить из одного общего скрина.
2. Для всей обязательной матрицы ввести совместимый безопасный серверный контракт: подтверждённый исход, стабильная категория причины, разрешённые параметры и допустимое действие. Сохранить действующие поля и потребителей. Известный отказ, операция в работе, unknown после отправки и ошибка чтения списка — разные состояния. Определённость исхода не подменять определённостью конкретной причины.
3. Связать существующие проверки readiness, ACL/membership, конфигурации, состояния операции и transport с безопасными категориями. Новые блокеры приглашения не вводить. Подкатегории провайдера — только по достоверному коду выбранного transport; для нераспознанной категории использовать общий подтверждённый отказ или unknown по фактическому исходу. Не выводить произвольный `item.error`, traceback, ключи и чужие данные, не угадывать причину по любому HTTP500. При ошибке чтения ответа после POST проверить адаптерный контракт: принятие письма может оставаться неизвестным.
4. Сохранять причину созданной попытки и возвращать те же факты после GET. Отказ до INSERT объясняется текущим ответом и может не иметь записи для GET; новую систему квитанций и фиктивные ID не создавать. Повторное чтение не превращает известный отказ в unknown. Состояние ссылки и регистрация остаются отдельными фактами; accepted означает принятие сервисом. Существующие ссылки, версии источников и legacy guards сохраняются.
5. Сохранить принятую компоновку списка. **Общий сбой — один блок над списком. Под статусом письма участника — краткая причина и доступное действие.** В карточке блок «Сведения о приглашении» по умолчанию свёрнут; раскрывается только для выбранного участника/попытки. Внутри — ID, время и безопасная диагностика с копированием. Обновление той же попытки сохраняет последнее действие раскрытия пользователя, включая действие во время чтения. Новая попытка или чужая карточка не наследуют раскрытие. Диагностику не выводить стеной текста; длинный ID не раздвигает mobile. Боковую панель не добавлять.
6. Показывать только работающие действия с существующим разрешённым переходом. Для unknown — проверить ту же попытку; для известного отказа после устранения причины — явная повторная отправка выбранным допустимым адресатам. Навигация ведёт в существующие сведения организации/участника. Кнопки настройки почты/связи/чужой диагностики без существующего действия и прав не добавлять. Доступное только оператору действие, которого нет в UI, объяснять текстом.
7. Сохранить batch и идемпотентность: точный нормализованный набор адресатов, отдельный исход каждого, прежний operation_id при unknown/readback, один эффект при повторной доставке команды. Не переотправлять принятым адресатам из-за ошибки одного. Поздний ответ не применяется к другому пользователю, организации, оценке или экрану. Readback остаётся ограничен тем же отправителем и разрешённой областью; новые права не вводить.

`Invitation_Behaviors_Draft.md` редакции 1.1 — обязательная спецификация реализации, включая тексты, состояния и размещение. Она различает код 2.1.26 и целевой контракт; наличие строки в спецификации не доказывает прежнюю реализацию. Корпоративное профилирование, новые источники и методологические правила этим заданием не меняются.

## Приёмка

| AC | Что принимаем | Достаточная проверка |
| --- | --- | --- |
| I1 | Вся матрица имеет реализацию и точное отображение | Параметризованные проверки реальных серверных ветвей и renderer: readiness, права/membership, конфигурация, transport, операции и безопасный fallback; без угадывания по строкам |
| I2 | Допустимая отправка работает через оба разрешённых пути | HTTP + изолированная тестовая БД + управляемый transport; один эффект на один ID |
| I3 | Причина сохранённой попытки не теряется после GET; отказ до INSERT объяснён текущим ответом | Сохранённые причина/параметры после readback; нет фиктивной записи и ложного unknown у pre-INSERT отказа |
| I4 | Timeout/потерянный или повреждённый ответ остаётся unknown до достоверного результата | Provider принял, клиент потерял ответ → нет дубля, тот же ID восстанавливает accepted; unknown не вызывает автоматическую новую отправку |
| I5 | Частичная отправка не дублирует успешных адресатов | Mixed accepted/failed/unknown, точная сводка и повтор только допустимого выбранного действия |
| I6 | Не раскрываются чужие операции и секреты, поздний ответ не меняет чужой контекст | Отрицательные HTTP-тесты прежних ACL и защиты actor/org/assessment/view; raw provider error в UI отсутствует |
| I7 | Layout читаем и работает на desktop/mobile | 1440/390/320: один общий блок над списком, причина под статусом, детали по участнику свёрнуты, ID переносится, нет неработающих кнопок |
| I8 | Lifecycle, ссылка и регистрация разделены | queued/sending/accepted/error/unknown, активная/истёкшая/отозванная/использованная ссылка, регистрация и назначение; accepted не назван доставкой |
| I9 | Подтверждённый отказ неизвестной категории отличается от неизвестного исхода | Разные тексты и допустимые действия; доверенные provider subcodes дают конкретику, отсутствующие подкатегории не выдумываются |
| I10 | Обновление сохраняет управление деталями той же попытки | Пользователь открывает/закрывает сведения во время чтения; последнее действие сохраняется, состояние не переносится к другому участнику/попытке |

Основные варианты проверять параметризованно на production handlers; браузер нужен для значимых переходов/доступности, не отдельный полный маршрут для каждой строки. Приёмка QA-02 не включает установление или устранение причины живого отказа. QA-05 возвращает диагностический результат; адресное исправление установленной причины определяется после его анализа. Controlled I2 подтверждает механизм, но не почтовую конфигурацию TEST.

Реальная доставка отдельно от transport accepted. В QA-02 реальные письма не отправлять. Проверка живой отправки/доставки возможна только по существующему отдельно разрешённому тестовому порядку с явными получателем и объёмом; до неё не утверждать «доставка проверена». Массовая повторная рассылка не является проверкой.

Откат: revert ограниченного diff с сохранением совместимости API. Конфигурацию среды эта карточка не изменяет. Существующие ссылки/операции и участников не удалять и не пересоздавать.
