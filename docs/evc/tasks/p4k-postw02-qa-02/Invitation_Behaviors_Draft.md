# Приглашения — спецификация состояний, причин и действий

Редакция 1.1 · 17.11.2026. Состояния, тексты, действия и размещение утверждены владельцем для реализации в QA-02. Эта редакция заменяет ограничение прежней редакции о проработке без внедрения. Проверенная исходная реализация: main `fffd501a51cae673a4e0ee87ec5d6cbc83069e21`, выпуск 2.1.26. Пути и ветви ниже описывают исходный код; целевое поведение реализуется и проверяется отдельно. Применим Product Architecture 1.0 + Change01 WORKING 01.10.2026, выбранный глоссарий и AGENTS/EVC; статусы источников не повышаются. Приглашения не меняют оценочную методологию.

## Главный принцип

Администратор и суперадминистратор видят **точную подтверждённую безопасную причину**, затронутых адресатов и доступное следующее действие. Неизвестный исход остаётся неизвестным. Сведения о последней попытке отправки, действующей персональной ссылке, регистрации и назначении оценки не заменяют друг друга.

Имеющийся API `PersonalInvitationResultItem` содержит status, error, invitation_id, expires_at, delivery_status, link_status; структурированных reason_code/retry_after/failure_stage сейчас нет (`Api/schemas.py:235–242`). Фраза «проверьте адрес и настройку почты» для всех item.error — подтверждённый дефект formatter (`web/js/screens/admin/organizations.js:87–105`). Категории ниже задают целевое поведение, но не утверждают наличие структурированных кодов в исходном API. В QA-02 ввести безопасный серверный контракт причины с совместимостью существующих ответов. Raw error не выводить: в нём могут находиться технические подробности провайдера.

Контракт различает факт исхода и подробность причины. Подтверждённый отказ неизвестной безопасной категории остаётся отказом; неизвестный исход после отправки остаётся unknown. Передавать стабильную категорию, разрешённые параметры, степень определённости и допустимое действие; конкретные имена новых полей выбрать по действующему API и записать в контракте. Причину сохранённой попытки возвращать после GET. Отказ до создания операции объяснять в текущем ответе; не создавать фиктивную запись или ID ради readback.

## Ссылка и регистрация показываются отдельно

Существующие факты: GET разделяет delivery_status и link_status (`routes.py:4233–4253`), карточка выводит отдельные строки (`organizations.js:2081–2094`). Сохранить это разделение и точный срок сервера в локальном времени.

| Состояние ссылки | Строка интерфейса | Что делать |
| --- | --- | --- |
| Не создана | «Персональная ссылка не создана» | Показать причину отказа последней попытки; исправить её |
| Действует | «Ссылка действует до [дата, время, часовой пояс]» | Дополнительная отправка — явное действие, не автоматический повтор |
| Истекла | «Срок ссылки истёк» | Явная повторная отправка после проверки текущего доступа |
| Отозвана | «Ссылка отозвана» | Новая отправка только при действующем решении о доступе; не отменять отзыв автоматически |
| Использована | «Ссылка использована» | Для зарегистрированного участника — обычный вход; не требовать повторной регистрации |
| Не удалось прочитать | «Актуальность ссылки не подтверждена» | Обновить состояние; старое accepted не доказывает актуальную ссылку |

POST сейчас проверяет used/revoked/expired совместно и возвращает одну ошибку (`routes.py:4073–4075`), тогда как GET их разделяет. Для точного текста использовать достоверное чтение, а не распознавание общей строки. Повторная успешная отправка отзывает предыдущие неиспользованные ссылки только после accepted (`routes.py:4160–4168`); не обещать, что старые ссылки отозваны при отказе новой попытки.

`is_registered` выбирается до отправки (`routes.py:3968–3971,4054–4057`), но не используется для отдельного отказа. Регистрация сама по себе не равна назначению оценки и не доказывает прохождение. `already_registered` в readback сейчас выводится из used_at; актуальную регистрацию карточка получает отдельным registration_status. Не смешивать эти источники при разработке новых текстов.

## Batch, роли, версии и размещение

- В batch показывать короткую сводку по подтверждённым исходам: «Приняты сервисом: 3. Не отправлены: 1. Исход уточняется: 1». Слова «доставлено всем» недопустимы без delivery events. Числа считать по точному нормализованному набору адресатов, не по последнему успешному ответу. Нельзя повторять весь batch из-за одного отказа и повторно отправлять принятым адресатам.
- Список сохраняет принятую композицию. **Под статусом письма конкретного участника — краткая причина и доступное действие. Общая проблема сервиса/сессии — один блок над списком.** В строках затронутых участников остаются краткие достоверные состояния без повтора полного общего объяснения. Статус оценки не заменяется статусом приглашения; боковую панель не добавлять.
- В карточке участника блок «Сведения о приглашении» по умолчанию свёрнут. Раскрытие относится только к этому участнику и попытке, не ко всему списку. Внутри — ID попытки, время, безопасная диагностика и копирование; нет токена ссылки, ключей, raw provider response или чужих данных. Обновление той же попытки сохраняет последнее действие раскрытия пользователя, включая действие во время запроса. Для новой попытки/другого участника чужое раскрытие не переносится. Длинный ID переносится внутри блока и не раздвигает mobile-карточку.
- Кнопка появляется только при существующем доступном действии. Unknown ведёт к проверке той же попытки; известный отказ после устранения причины — к явной повторной отправке допустимым адресатам. Навигация ведёт в существующие сведения организации/участника. Операторскую настройку, которой нет в UI, объяснять текстом без неработающей кнопки.
- Доступный администратору фактический отказ не скрывать словом «ошибка». Суперадминистратор видит ту же причину в своей разрешённой организации; полномочия не равны доступу к ключам transport. Не добавлять несуществующую кнопку «Настроить почту»/«Связаться с ответственным». Техническую конфигурацию правит оператор через существующий процесс.
- Readback ограничен **тем же отправителем + организацией + assignment_ref + operation_id** (`routes.py:4217–4224`). Суперадминистратор не получает автоматически readback чужой попытки. Если требуется общая поддержка чужих операций, это отдельное решение о разрешённой диагностике, а не обход этого фильтра.
- При смене пользователя/организации/экрана клиент не должен применять поздний ответ (`organizations.js:980–989`); идентичность локальной операции сохраняется до POST и переживает reload. При неизвестном результате сначала восстанавливать прежний ID; известный отказ допускает явное новое действие после устранения причины.
- Приглашение сейчас привязано к `assignment_ref` и проверяет последний подтверждённый ранний минимум анкеты, а не к версиям опубликованной программы/роли/execution snapshot (`questionnaire_sources.py:256–266`, `routes.py:3934,3959`). Нельзя заявлять пользователю «не опубликована программа 1.2» или «роль не подготовлена», если конкретная ветвь этого не проверяла. При рассогласовании выбранной программы нужно брать подтверждённый безопасный контракт готовности; не вводить новые блокеры приглашения молча.
- Сервер формирует безопасную категорию причины и разрешённые параметры; UI использует согласованный словарь. Совместимость старого item.error сохраняется без вывода произвольного текста. Для подтверждённого отказа неизвестной безопасной категории: «Приглашение не отправлено. Причину отказа пока не удалось уточнить». Для неизвестного исхода: «Не удалось подтвердить отправку. Проверьте эту попытку». Различаются также доступные действия. Специализированную причину провайдера показывать только при достоверном подтверждении; отсутствие подкатегории не разрешает выдумывать её.

## Обязательные уточнения реализации

1. Повреждённый JSON ответа Unisender сейчас считается EmailDeliveryError (`email_service.py:114–117`), хотя после фактического POST нельзя исключить принятие письма только по невозможности разобрать ответ. При реализации проверить provider contract; до подтверждения трактовать как неопределённый исход, а не предлагать безусловный повтор.
2. Backend sending-uncertain текст советует новый operation_id (`routes.py:4108–4111`), клиент при этом сохраняет прежнюю identity и предлагает readback. Унифицировать смысл: неизвестный исход — проверить прежнюю попытку; потенциально дублирующая новая отправка требует отдельного явного действия.
3. У per-item отказов нет структурированного safe кода, а warning в routes.py:4179 не содержит причины/operation_id. Часть отказов происходит до создания строки БД. Для диагностики текущего сбоя нужны безопасные коды и корреляция, а не один текст в UI или номер подготовки оценки (он относится к другой операции).
