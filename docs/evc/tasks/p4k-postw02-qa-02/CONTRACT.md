# QA-02 — контракт приглашений invitation_reason/1

Дополнение совместимо с прежними POST/GET и полями status/error/invitation_id/
expires_at/delivery_status/link_status. Схема БД, права, маршруты и версии источников
не изменены. error сохраняет строковый тип, но содержит только безопасный текст/код.
Старый произвольный error не попадает в отображение, data-атрибуты или сохранение
клиентского восстановления. Renderer принимает только разрешённые поля.

| Поле | Значение |
| --- | --- |
| outcome | accepted / failed / pending / unknown; для списка без попытки not_attempted |
| reason_code | Стабильный код из `Api/invitation_outcomes.py:REASONS` |
| reason_params | Только missing_fields из purpose/organizer/results_usage; retry_after_seconds — целое 0–86400 при provider_limit |
| next_action | none/check/retry/retry_later/review_member/review_organization/operator/refresh_context |
| failure_stage | recipient/readiness/access/configuration/transport/operation/finalization/complete/unknown |
| operation_id | ID команды, не квитанция отправки; у отказа до INSERT записи GET может не быть |
| created_at | UTC Z сохранённой попытки, если доступна |
| replayed | Повторная команда прочитала сохранённый исход; новых писем нет |

Delivery определяет определённость outcome, категория причины её не подменяет.
Старое error без безопасной категории → failed_unclassified при delivery=error.
Неполный/неразобранный ответ после POST, timeout, сетевой/протокольный обрыв и
неподтверждённый 5xx → unknown. Подтверждённое структурированное отклонение → failed;
подтип берётся только из кода адаптера. Поля ссылки и текущая регистрация отдельны;
already_registered в legacy GET не переопределяет delivery_status/outcome.

Без миграции: delivery_error хранит JSON envelope invitation_reason/1 с разрешённой
диагностикой и SHA256 точного нормализованного набора адресатов. Адресаты всего batch
не копируются в каждую запись. Accepted также сохраняет fingerprint; произвольный
сырой provider response не сохраняется. Legacy plain text читается безопасным
fallback; его причина не угадывается по тексту. Для legacy без fingerprint не
приписывается задним числом знание первоначального полного набора; действующие
actor/organization/assignment/token guards сохранены.

Блокировка команды PostgreSQL advisory lock связывает проверку identity и эффекты
при конкурентных запросах. Ожидание ограничено2секундами, затем pending/unknown;
владелец использует одно соединение до release в finally. Нет фоновой очереди,
повторной рассылки или нового права. Новый нормализованный набор с прежним ID
отклоняется. Повтор известной ошибки читает сохранённую причину даже после изменения
readiness. Pre-INSERT отказ остаётся в текущем ответе; фиктивной строки нет.

GET ограничен прежними sender+organization+assignment_ref+operation_id. В списке
ID операции возвращается только её отправителю. Чужому администратору не добавляется
возможность readback; безопасные сведения участника остаются в прежней области ACL.
Клиент удерживает ID до достоверного исхода, сохраняет известные результаты при
частичном ответе, проверяет прежнюю команду, блокирует пересечение с нерешённой
командой. Явный новый retry отказавшего адресата не включает принятых из старого batch.
Обновление списка после accepted не меняет исход и не вызывает повтор POST.

UI: общий сбой один раз перед списком, у участника локальная безопасная причина,
действия используют существующую навигацию/команды. Операторская настройка объясняется
текстом. Доступное readback из серверной записи работает и без локального pending.
Сведения в карточке свёрнуты; живая open-семантика не заменяется сохранённым перед GET
значением. Новая карточка/attempt key не наследует open. Копируются только ID/время/
безопасное описание; длинный ID переносится.

Адаптеры: официальные [Unisender Go](https://godocs.unisender.ru/web-api-ref) и
[Postmark](https://postmarkapp.com/developer/api/overview), чтение17.11.2026.
Unisender101/102/105/106/215 → доступ;206 → отправитель;901 → лимит.
Postmark10 → доступ;406 → адресат;100 → временный отказ. Неоднозначные коды300/403
не объявляются ошибкой адреса. HTTP429 имеет надёжную общую категорию ограничения;
произвольный HTTP400/500 не даёт подкатегории адреса/ключа/отправителя. Для5xx после
POST без гарантированного отказа исход unknown. Retry-After адаптером не извлекается:
точное время ожидания не выдумывается. Никакого автоматического transport retry.
