# UX-ADM01: данные организации и готовность приглашения

## Результат

Администратор ведёт сотрудников отдельно от данных оценки, подтверждает единый источник
анкеты для конкретной оценки и может отправить приглашение только после серверной проверки
раннего минимума этой оценки. Участник видит сведения именно своего приглашения.

## Область

- Включено: существующий ADD02 intake, привязка к `assignment_ref`, серверный gate единичной
  и массовой отправки, безопасная проекция API, переходы «Участники»/«Данные организации».
- Не входит: Stage 2 и дополнительные пять минут, новый редактор программ, запуск Cycle,
  методологическая приёмка, реальные письма и межбраузерная приёмка владельцев.

## Ограничения и риски

- Старые участники без однозначного приглашения продолжают legacy W02 только при отсутствии
  нескольких подтверждённых оценок; неоднозначность блокируется.
- Реальные email не используются. `assignment_ref` — существующая техническая ссылка, а не
  право произвольного назначения.
- Изолированная PostgreSQL integration обязательна в CI; локально — только при наличии
  безопасного `TEST_DATABASE_URL`.

## Критерии приёмки

- [x] Черновик анкеты не блокирует добавление сотрудников и не отправляет письма.
- [x] Неподтверждённый early minimum блокирует API отправки; подтверждённый разрешает её.
- [x] Два `assignment_ref` одной организации не подменяют briefing друг друга.
- [x] UI различает готовность приглашения и дальнейшую готовность назначения.
- [x] API не возвращает raw source/checksum/idempotency metadata в обычный UI.
- [x] Начатые Cycle и опубликованные snapshots не переписываются.

## Откат

Откат к merge-parent возвращает прежнее поведение; nullable `assignment_ref` и
`briefing_json` можно оставить без влияния. Новые подтверждённые редакции неизменяемы и не
удаляются; старые OrganizationContext/Cycle продолжают читаться по прежнему контракту.
