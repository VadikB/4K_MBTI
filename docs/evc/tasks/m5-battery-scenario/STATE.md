## Контуры и границы

- [Связи сценариев 1.6.0](../../../../assessment_definitions/cases/competencies_4k/functional-personalization-runtime/1.6.0/manifest.json)
  применяются по версии и SHA паспорта из банка 0.7. Сценарный движок использует
  исходные условия, аудитории, ограничения, завершение и связи наблюдаемости.
- Явный `scenario_tests=True` при создании диагностического Cycle закрепляет
  QA-маршрут, источники C‑23, M2/M3, правила, провайдера и пакеты промптов.
  Если с профилем связана действительная учебная роль, используется snapshot
  точного назначения. Без подтверждения мандата SPEC.09 возвращает
  `M5_BATTERY_PROFILE_CLARIFICATION_REQUIRED:18/professional_recommendation`.
- Для First и Next `Api.m5_battery_preparation.prepare_next` использует общий
  сервис PM‑03 и запись C‑34. Next ждёт отдельного закрытия прежней AS.
  Gateway поставляет конкретные тексты. До проверки сервер связывает старт,
  события, ссылки наблюдаемости и версии. Логи сохраняют SHA ответа и SHA
  собранной версии. Tester, Challenger и компилятор работают с одним собранным
  кандидатом на круг, включая repair. Авторские AS в запросах отсутствуют.
- Исполнение использует штатные `start`, `submit_turn_detached` и
  `transition`. Письменный ведущий не входит в набор активных ролей. Факты F
  и ещё не предъявленные документы хранятся отдельно от публичного материала.
  Журнал фиксирует автора, отправителя и аудиторию, а также подтверждённые
  реплики. В C‑45 проектная возможность отделена от фактических ходов.
- QA-обход существующего допуска сохраняет WORKING и решение о недопуске к
  оценке людей. Содержательный протокол новой батареи и совместный прогон
  с обновлёнными проверяющими остаются предметом 03. Живая модель не вызывалась.

## Матрица управляемого шлюза

| Case | Входной ход | Событие, адресат и наблюдаемый результат |
| --- | --- | --- |
| SPEC.01 | Посторонний вопрос, два перефразирования срока, предложение следующего шага | Посторонний ход не выдаёт данные. E02_REPLY даёт Заказчику только F01 для ответа участнику. На продолжаемом предложении E01_DOCUMENT предъявляет M02 один раз. Ранний финал с вопросом оставляет M02 закрытым. |
| SPEC.02 | Пояснение предъявленного пакета, запрос будущего результата, явная неполная сдача | P00 и M01–M06 на старте. E01_FACT и E03_UNKNOWN отвечают через ведущего. E02_SUBMISSION завершает сценарий без нового документа. |
| SPEC.03 | Конкретное предложение совместной работы, адресная передача C1, обещание переслать, подтверждённая пересылка C2 | E01_UPDATE после фактических реакций доставляет M04 от C2 только участнику. E02_TRANSFER хранит точную цитату и её аудиторию. C3 не получает частную цитату C1. Принятая пересылка C2 несёт только разрешённый фрагмент. |
| SPEC.04 | Существенный замысел, доработка, явный финал | M05 один раз в первой реплике Заказчика. E01_REVIEW и граница объединены; E02_REVISION относится к фактической доработке. F остаются закрыты до адресного условия. |
| SPEC.05 | Предложены два рабочих способа, запрошена позиция коллеги | M05 открывает разговор. Реакция и подтверждённая поддержка C1 записаны одной репликой; распоряжение ресурсом не возникает. |
| SPEC.06 | Запрошен вклад всех сторон, отдельно согласована подготовка | C1, C2 и C3 отвечают по своим функциям. Подтверждён только вклад C1 в подготовку; результат будущей пробы неизвестен. |
| SPEC.07 | Пояснение пакета, вопрос о будущем результате, явная неполная сдача | E01_EXPLAIN и E03_UNAVAILABLE отвечают через ведущего по известным данным; E02_SUBMISSION завершает письменную ситуацию. |
| SPEC.08 | Адресная отправка версии 4 и обещание передать остальное после внешнего согласования | Фактическая передача и подтверждение R_RECIPIENT имеют отдельные записи. E03_PENDING сохраняет открытый внешний статус. Обещание передачи не создаёт. |
| SPEC.09 | Условная рекомендация с вопросом о повторной проверке | R_MANAGER отвечает на границу основания. Кандидат и HR не становятся собеседниками. Профиль без подтверждённого мандата возвращается на уточнение до запроса к шлюзу. |

Сценарий First → Next проходит с SPEC.01 на SPEC.02 после отдельного AS_close.
Отдельная проверка BANK-01 устанавливает диагностический банк посреди уже
начатого прежнего цикла и читает старую AS и Next по прежней версии. Есть
регрессии неизменяемого адресного SPEC.03, ошибочного кандидата, repair и
восстановления учебной роли из закреплённого snapshot.

## Воспроизведение и откат

В изолированной PostgreSQL с отдельным `TEST_DATABASE_URL`:

```sh
.venv/bin/python -m pytest --run-integration -q \
  tests/integration/test_m5_battery_scenario_db.py \
  tests/integration/test_m5_battery_bank_db.py \
  tests/integration/test_m5_addressed_spec03_db.py \
  tests/integration/test_m5_cycle_runtime_db.py \
  tests/integration/test_case_admission01_db.py
```

Для отката новых диагностических запусков используйте обычный режим BANK-01
без `scenario_tests=True` или прежний каталог. Закреплённые тестовые AS требуют
совместимого исполнителя 02 при возобновлении. Исторические банки и снимки
используют прежние обработчики. Миграции БД отсутствуют.
