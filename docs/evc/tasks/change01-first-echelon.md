## E1 — CaseVersion и допуск AS

Результат: C-23/24/34 валидируют профиль, точные цели и ролевые условия перед
предъявлением. Область: новые версии assessment_case_contracts и loaders,
M5 lab как технический адаптер, контрактные fixtures. Не входит: утверждение
новых Cases, маршрутизация M7, расчёты M6.

Предлагаемый namespace нового пакета — отдельная schema version, без изменения
существующего cases/competencies_4k/1.1. Версию методологии не использовать вместо
schema_version. Точные пути и регистрация loader фиксируются в E1 до записи пакета.
Предметный prompt — новая версия артефакта, не строка Python.

Приёмка: T01–T03 на fixtures минимум двух ролей; формат PASS не подменяет Case QA.
Отказ по каждой неразрешённой ссылке/роли/цели объясним. Новые Cases нужны для
предметного допуска, не для реализации схемы. Проверки: backend, HTTP нового пути,
integration при изменении mapping/хранения, diff; CI.
Откат: отключить новый loader/entrypoint, старые пакеты неизменны.

## E2 — фиксация входов и проверка снимка

Результат: продолжение нового прохождения не читает active profile и текущие
Case-параметры. Область: preparation, snapshot, все читатели диалога, validation.
До кода записи подготовить expand-схему и матрицу старых/новых читателей.
Legacy без provenance маркируется явно; массовый backfill исключён.

Приёмка: T01/T03/T04/T09; изменение текущих таблиц/конфига после старта не меняет
использованные условия, битый snapshot отклоняется; snapshot и checksum проверяются
на открытии, ходе, восстановлении и передаче в evaluator. Проверки: backend + HTTP
+ integration на изолированной test-БД. Зависимость: формат E1.
Откат: запретить новые запуски нового пути, сохранить чтение и историю новых записей.

## Два рубежа приёмки

Технический: E1–E3 исправлены и проверены до общего прогона; E4–E6 имеют согласованные
реализованные потребители и passing contract/integration. Фикстуры и stub допустимы,
их статусы явно ограничены. Согласованность контрактов проверяется до связующего кода.

Содержательный: новые допущенные CaseVersion/AS, экспертные ожидания и GC; реальные
прогоны отдельно от стандартных тестов, результаты и ограничения зафиксированы.
Ожидание Cases не задерживает техническую подготовку и проектирование E4–E6.

Все изменения схемы проходят план совместимости и восстановления до исполнения.
Deploy/публикация CURRENT/утверждение baseline — отдельные решения, не следствие
данных постановок. Конкретные исполнители и сроки не назначены; владелец продуктовых
приоритетов — пользователь, технического решения — архитектор, содержания — методолог.
