## Решение и трассировка

| Отображаемое состояние | Фактический серверный источник | Реализация и проверка |
| --- | --- | --- |
| Ранний минимум | `assignment_readiness`: последняя подтверждённая редакция по `organization_id + assignment_ref` и обязательные поля briefing | `admin_assignment_readiness`; unit, HTTP, PostgreSQL |
| Черновик не подтверждён / данных нет | последняя редакция того же `assignment_ref`; отсутствие подтверждённого раннего минимума | unit и browser |
| Контекст | `organization_context_version_id` подтверждённой редакции; отдельного клиентского решения нет | server projection и browser |
| Роли / поздний gate | существующий `acquaintance.late_readiness` для каждого участника с явно переданными выбранными `organization_id + assignment_ref` | unit, PostgreSQL, browser переключения двух оценок |
| Идёт подготовка | активная пользовательская очередь `assessment_preparation_jobs` со статусом `queued/running` | server projection и unit |

- Проекция добавляется к list/preview/confirm анкеты; после confirm интерфейс сразу
  получает актуальное серверное состояние. Неизвестное состояние и ошибка HTTP не
  преобразуются в `ready`.
- UI только переводит серверные статусы в понятные подписи и даёт переходы к данным
  организации или участникам. Checkbox готовности и клиентский расчёт gate отсутствуют.
- Добавление участника остаётся доступным независимо от заполнения анкеты; приглашение,
  назначение и начало оценки продолжают проверяться существующими серверными gate.
- Смена `assignment_ref` выбирает только соответствующую revision/readiness и повторно
  отрисовывает экран; fallback к чужой оценке удалён.
- Org-admin редактирует имя, код и профиль единственной закреплённой карточки через
  существующий scoped `PATCH`. Свободный tenant create скрыт; отсутствие/отзыв scope
  показывает безопасное состояние ожидания. Домены, назначение администраторов и
  создание новых tenant остаются только у superadmin.
- Прямой API сохраняет серверный запрет: `POST` для org-admin обновляет ровно одну
  закреплённую организацию, пустой/неоднозначный scope и подмена ID дают `403` без записи.

## Проверка и откат

- Unit/HTTP регрессии покрывают состояния readiness, единственный scope, отсутствие и
  неоднозначность scope, а также подмену ID организации.
- PostgreSQL regression на изолированной БД проверяет фактические запросы и отсутствие
  смешения двух `assignment_ref`.
- Browser-сценарии выполняются с ролью org-admin: редактирование закреплённой карточки,
  отсутствие free create, независимое добавление участника, переход к ролям,
  переключение двух оценок и безопасное состояние при ошибке readiness-запроса.
- Фактические команды, полный локальный минимум и CI фиксируются в PR.
- Откат: revert PR. Новых таблиц, колонок и преобразований данных нет; расширенные
  поля HTTP-ответа совместимы со старыми потребителями.

## Ограничение и следующая зависимость

`assessment_preparation_jobs` является пользовательской очередью и не содержит
`assignment_ref`; поэтому UI честно показывает активную подготовку участников
организации, но не утверждает отсутствующую привязку job к выбранной оценке.
Расширение контракта очереди — отдельное архитектурное решение, не условие этой задачи.
