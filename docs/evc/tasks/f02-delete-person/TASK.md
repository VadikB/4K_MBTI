# F02 — Удаление человека и его аккаунта

## Результат и основание

Прямое поручение владельца 11.11.2026: «возьми в работу» применительно к
`P4K-F02_Delete_Person.txt`, версия 1.0 / 11.11.2026. Файл требований хранится
рядом с архитектурными материалами в `обработка замечаний/путь от создания
организации до начала оценки`. Новое поведение заменяет прежнее exclude/retain
из COM D01/SUP01–06 и FIX02 F01/F02 только в области удаления человека.
«Снять права» остаётся отдельной командой. Остальные карточки не запускаются.

База после `git fetch origin main`: `748be43e55587aa3b7e3a3945189c5ac737f59eb`,
приложение 2.0.97; рабочее дерево изначально чистое. Одна ветка
`codex/f02-delete-person`, одна локальная задача и одна будущая точка PR.

## Решения, совместимость и стоп-условия

Существующий механизм полного удаления переиспользуется: preview/fingerprint,
блокировки, транзакция, обезличенный receipt, внешний deletion ledger.
Org-admin получает доступ только после проверки всей области удаления своей
допустимой цели. Configured accounts, self и последний администратор защищаются
на сервере. Legacy `is_participant=false` автоматически не удаляются; подготовить
адресный план происхождения и перехода без нового интерфейса исключений.

Все восемь стоп-условий рабочего цикла: **нет** для локальной реализации:
новая семантика/права прямо заданы F02; контракт и потребители рассматриваются
в одной задаче; массовой миграции, новых методологических норм/артефактного контура,
выпуска и действий вне F02 нет. Удаление необратимо по существующему контракту;
revert кода не восстанавливает удалённые данные. Непредусмотренный новый конфликт
блокирует только зависимую часть.

## Полномочия этапа

Разрешены локальная реализация, адресные и общие проверки, сборка, review,
собственные локальные коммиты и подготовка описания одного PR. Файл требований
не считается самостоятельным разрешением внешних побочных эффектов.

`branch_push=false`, `pr=false`, `merge=false`, `deploy=false`,
`version_bump=false`, `artifact_publish=false`. У пользователя пока нет прямого
поручения публиковать результат этой задачи. Старые полномочия из STATE других
задач не используются. Подготовка локального review продолжается без ожидания.

Синтетические проверки только на собственной PostgreSQL с test/pytest в имени
и проверкой ownership marker. Не читать `.env`, секреты/реальные персональные
данные; не отправлять письма, не вызывать платный LLM, не менять пользовательские
данные и не обращаться к рабочей БД.

## План

1. Разведка и фиксация контрактов/границ — завершены.
2. Backend и frontend F02 с регрессией — активно.
3. Проверка существенного пути UI → HTTP → PostgreSQL, независимые отрицательные
   readback и контрольные данные; отказы, токены, late jobs, lost response/storage.
4. Полный применимый локальный минимум, review, один локальный результат,
   CHECKS/STATE и PR description. По каждому F02-AC01–05 точные PASS/FAIL/NOT_RUN,
   данные, expected/actual, SHA и evidence. Owner visual остаётся PENDING.

## Проверка и откат

По матрице: diff-check, lint/build, frontend regression, backend unit/HTTP,
integration на собственной PostgreSQL, actual browser по изменённому пути.
CI/main/TEST отдельно от локального PASS. Без remote PR новый CI NOT_RUN.

До выпуска откат = локальный revert изменений F02. После выпуска revert кода
прекращает новые операции, но не отменяет подтверждённое удаление. Ledger и receipts
сохраняются; restore backup допускается только с существующим replay/runbook.
