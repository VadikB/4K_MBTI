1. РЕЗУЛЬТАТ И ОСТАТОК

История и immutable snapshots A не изменяются. Повтор B, reload/две вкладки не создают дубль эффекта или повторный старт времени.
На main5a47e10 дефект F03 остаётся: _current_cycle выбирает по owner/org/config/profile/status без assignment ID; prepare возвращает старый Cycle, start_prepared закономерно отказывает ASSIGNMENT_CANCELLED. Главный обязательный новый proof — исправленный actual HTTP/owned PG и один browser-маршрут.
Шесть BaseRoles, пилотный specialist_expert, независимые admin-права, современные stage/history/counters и effective_confirmed уже существуют. Их не создавать заново. PR214 F05/F06 не повторять. F12/F16 остаются ограниченными регрессиями, а не отдельными проектами UI/дашборда.

РЕСУРСЫ, ОЖИДАНИЕ И РАСХОД — ОБЯЗАТЕЛЬНО ДЛЯ ЭТОГО ПАКЕТА
Этот раздел уточняет прежние правила lifecycle; при расхождении о сохранении диагностики применяется правило «сохранить данные, остановить вычисление». Критерии продукта и CI не ослабляются.
До запуска в существующем STATE записать task/run ID, владельца, container ID/name и restart policy, PID/PGID собственных servers/workers/browser runners, порты, приватный state/volume, команды запуска, проверки и остановки. Не выводить credentials/DSN/owner marker. Не вводить новый сервис учёта: достаточно раздела существующего STATE. Зафиксировать исходные ресурсы, чтобы отличать свои от чужих. Поочерёдно создавать только нужный контур, переиспользовать штатный runner и уже готовые fixtures.
Временные Docker-контейнеры запускать с restart=no; для Compose временного стенда — restart: "no". Не создавать launchd/systemd/cron/watchdog/keep-alive/restart loops. Нельзя менять политику постоянных продуктовых сервисов. Запрещено оставлять активный preview «для будущей визуальной приёмки». Сохранить команду его воспроизведения и требуемый SHA/fixture; после проверки остановить.
Для каждой команды/ожидания заранее выбрать wall-clock deadline и критерий нового прогресса. Брать действующий timeout конкретного runner; если его нет — явно задать соразмерный предел до запуска, не ждать бесконечно. Технический deadline не изменяет продуктовые TTL/7200/259200 и не становится основанием закрытия оценки. Polling ограничен deadline и числом повторов; при отсутствии нового результата завершить ожидание, снять один bounded status/log snapshot и диагностировать. Повтор — только после установленной причины/изменения, без циклического CI polling и повторного полного suite. Истечение ожидания CI не означает отмену чужого/общего workflow: записать run/job/SHA, прекратить локальный poller, продолжить наблюдение отдельным явным действием.
Timeout оболочки не доказывает остановку descendants/Docker. Использовать штатную остановку сервера/worker и своё управляемое process group; дождаться выхода в ограниченный срок, затем адресно завершить только свои зависшие процессы. Никаких killall/pkill всех python/node/postgres, docker system prune или down чужого Compose project. Контейнер останавливать по записанному ID с ограниченным grace period; при необходимости адресной принудительной остановки записать причину, не применять FORCE к чужой/рабочей БД. Не создавать новые volumes/DB при каждом повторе без учёта предыдущих.
Нормальный успех, известный FAIL, timeout, исключение, прерывание/диагностическая остановка и передача другой сессии проходят один finally/штатный teardown: сохранить безопасный нужный operation/readback/evidence, остановить свои workers и приложения, остановить/убрать принадлежащие задаче временные ресурсы и подтвердить фактическое завершение. Если unknown/export failure требует сохранить DB/state, НЕ удалять данные: остановить временный контейнер/сервер без удаления нужного volume, сохранить приватное расположение и точную команду восстановления, пометить DATA_RETAINED_COMPUTE_STOPPED. Не держать вычисление запущенным ради диагностики. Если сохранить диагностику и остановить безопасно не удалось — записать конкретный blocker/остаточный ресурс, не заявлять cleanup PASS.
Подтверждение — не «stop отправлен», а container inspect running=false/restart=no, PID/PGID больше не работают, worker/browser poller завершён, свои порты не слушаются; при обычном cleanup штатно доказано отсутствие owned DB/state. Для сохранённого volume отдельно DATA_RETAINED, а не ложное database_absent. Один короткий resource-before/after в STATE/CHECKS, без новой системы отчётов. При аварийном завершении самого агента finally не гарантирован: следующий запуск сначала сверяет STATE и завершает оставшиеся именно свои ресурсы. Старые контейнеры неизвестного владельца автоматически не трогать.
Это условие завершения/передачи задачи, а не требование ещё одного полного продуктового прогона. Локальные контейнеры сами по себе не доказывают источник расходов LLM: отдельно учитывать активные provider workers, реальные запросы, retries, model/calls/tokens по доступным первичным данным. Платных LLM, реальной почты и мутаций общего TEST этим поручением нет; исключение07 только после отдельного конкретного допуска.
