## Выявленные ограничения

1. **Runtime admission отсутствует.** Все Case имеют статус WORKING. Лист прямо
   фиксирует `Диалоговый прогон — NOT RUN` и `Время, трудность, устойчивость — NOT RUN`.
2. **Нет AS QA.** Поля персонализации описаны, но ни один Case не применён к
   зафиксированному PersonalizedProfile T08.5; сохранение условий не проверено.
3. **Не разрешён источник CT.** Имена и функции CT нельзя объявить независимо
   подтверждёнными только по этой выгрузке или старому архиву v0.4.
4. **Высокая проектная плотность.** Один Case содержит 8–9 Indicators и 3–5 CT
   при 25–40 минутах. Это не структурная ошибка, но эмпирический риск потери
   отдельных условий и перегрузки. Решение возможно только после прогонов, без
   автоматического сокращения target set.
5. **Одна BaseRole на версию.** Это допустимо и упрощает проверку. Формат
   «многоролевой диалог» означает персонажей, а не несколько BaseRole оцениваемого.
6. **Печатный вид неудобен.** Стандартный экспорт LibreOffice создаёт 62 страницы,
   поскольку широкие таблицы разбиваются по группам столбцов. Данные читаемы, но
   для human review нужен отдельный review/export view либо настроенные print areas.
   Это не блокирует машинный импорт.
7. **Происхождение неполно.** Указан hash исходного DOCX, но сам файл не приложен;
   нельзя проверить полноту/тождественность Excel-выгрузки источнику.

## Предлагаемая реализация

### 1. Разделить редактируемый master и снимки импорта

- Рабочий XLSX остаётся редактируемым master-файлом и может изменяться в ходе
  командного обсуждения без регистрации каждой промежуточной правки.
- Перед воспроизводимой проверкой, Case QA или загрузкой создавать неизменяемый
  source snapshot с номером редакции, checksum, датой и ссылкой на задачу T08.6.
  Проверенный здесь файл является кандидатом на snapshot `v0.1`, а не последней
  редакцией master навсегда.
- Изменение текста, целей, ролей, сценария или материалов после snapshot создаёт
  следующую редакцию источника и новую CaseVersion. Редакционные изменения, не
  влияющие на Case, всё равно получают новый source checksum. Номер CaseVersion
  задаёт владелец артефакта; валидатор лишь запрещает публиковать изменённое
  каноническое содержание под уже известной парой CaseID/CaseVersion.
- Зарегистрировать отсутствие исходного DOCX и каталога CT в source manifest.
- `Варианты` хранить как design backlog, исключить из runtime package.

### 2. Добавить технический XLSX adapter в package/schema v2

Адаптер читает таблицы по именам Excel Tables, а не по координатам:

- `CaseCatalog` → обзор CaseVersion;
- `CasePassports` → 22 нормативных поля;
- `CaseParticipants`, `CaseData`, `CaseScenario` → scenario content;
- `CaseIndicators` → `indicator_targets`;
- `CaseApplicability`, `CaseTypeLinks` → отдельные связи;
- `ExportDescription` → provenance/rules, но не admission evidence;
- `FutureCaseIdeas` → исключённый design artifact.

Сборщик проверяет уникальность ключей, полный набор 22 полей, точное совпадение
нормализованных листов с паспортом, M2 refs/иерархию, M3 role, CT refs, scenario/data
refs и canonical checksum. В Python остаются только разбор формата, универсальные
инварианты ссылочной целостности и технические ошибки. Содержательные строки,
перечни целей, сценарные правила, QA-траектории и состав evidence допуска хранятся
в versioned artifacts и не встраиваются в Python.

Состав обязательных evidence и допустимые результаты задаются отдельным versioned
admission-policy artifact. Общий evaluator читает эту политику и проверяет evidence;
он не содержит захардкоженного перечня M5-проверок. XLSX adapter также не исправляет
и не дополняет содержание: при неизвестной ссылке или неполном контракте он
возвращает ошибку с координатой источника.

### 3. Собрать пять immutable CaseVersion

- Package namespace: `assessment_definitions/cases/competencies_4k/1.1/`, schema 2.
- Для снимка этого анализа Case version сохраняется как `v0.1`; следующая
  содержательная редакция master получает следующую CaseVersion. Package/schema
  имеют отдельные версии и не следуют автоматически за номером XLSX.
- Каждая из 43 целей хранит M2 ref, Skill/Component, ObservationCondition,
  ObservableAction и ValidityRisk.
- Полный CaseVersion получает checksum; поля PARTICIPANT отделяются от INTERNAL.
- Package остаётся `draft/WORKING`, `runtime_enabled=false`.

### 4. Загрузить как quarantined candidate pool

- Сначала `--verify-only` без соединения с БД.
- Затем транзакционная загрузка в выбранное заданием T08.6 immutable storage.
  Отдельная БД или второй каталог из-за слова `pool` не создаются; expand-схема
  нужна только для отсутствующих refs/materials/rules/evidence после карты данных.
- Все пять Case получают `format_validation=PASS`, но `case_qa=NOT_RUN` и не
  входят в user-eligible pool.
- Повторный импорт того же hash идемпотентен; тот же ID/version с другим hash
  отклоняется. Старый файловый пакет v0.4 удалён из актуального дерева по решению
  владельца; история его состояния остаётся доступна в Git.

### 5. Исполнить Case QA

Для каждого Case и его единственной BaseRole выполнить минимум четыре группы
траекторий из источника: содержательное продвижение, преждевременное решение,
отказ/эскалация и управление остановкой. В последней группе пауза/возобновление и
окончательное прекращение проверяются как разные состояния. Дополнительные ветви
`CASE-TDISC-03/04` проверить отдельно. Эти траектории — минимум данного пакета,
а не универсальный достаточный Case QA.

Сохранять фактические Turns/events, раскрытые и нераскрытые данные, срабатывание
условий каждого Indicator, подсказки персонажей, время, дефекты и retest. Исправление
содержания после дефекта создаёт новую CaseVersion, а не переписывает v0.1.

### 6. Исполнить AS QA

- Взять frozen PersonalizedProfile T08.5 с допустимой BaseRole.
- Построить AS через общий builder, сохранив исходный target set 1:1.
- Проверить инвариант, полномочия, материалы, условные ветви и доступность каждого
  обязательного условия до первого Turn.
- Потеря условия даёт AS FAIL/not ready; Indicator нельзя удалить для получения PASS.
- После старта AS не регенерируется.

### 7. Допуск и test

- Первая версия admission-policy artifact требует три отдельных evidence:
  format validation PASS, Case QA PASS точной версии/роли и AS QA PASS точного
  snapshot. Изменение состава проверки оформляется новой версией политики, а не
  правкой условных ветвей Python.
- На test показать Case/AS/Profile refs, 43 цели по соответствующим Case,
  checksums, QA runs и причины отказа; IndicatorIDs не показывать оцениваемому.
- До выполнения QA основной runtime при выборе этих Case возвращает
  `AS_NOT_ADMITTED`, без fallback на старый каталог.
- После допуска M7 выбирает Case и управляет бюджетом; M5 не собирает сессию.

## Проверки и откат

- Unit/artifact: parser, таблицы/ключи, M2/M3/CT refs, deterministic build,
  canonical checksum и schema v2 rejection cases.
- Integration на изолированной БД: idempotent import, conflict, transaction rollback,
  quarantine, evidence и immutable read-back.
- HTTP/e2e: admitted/not-admitted C-34, роль, target mismatch, отсутствие fallback.
- LLM: stub в стандартном наборе; реальные диалоги только marker `llm`.
- Откат: не активировать package либо выключить opt-in; сохранить imported candidates
  и QA trace для аудита; старые данные не удалять и не backfill.
