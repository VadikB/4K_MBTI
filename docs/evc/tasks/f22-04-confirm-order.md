# F22-04 — порядок применения confirm и сохранность нового ввода

## Результат и основание

Основание — F22-04 P1 из `P4K_Full_Verification_2026-10-22.txt`. Поздний ответ
confirm больше не вытесняет более новую серверную редакцию. Изменённый после
отправки confirm ввод сохраняется как собственный draft и не удаляется ответом.

## Источники, границы и решение

Прочитаны `README.md`, `CONTRIBUTING.md`, обязательный EVC workflow и verification
matrix, Change 01 `1.0/01` (WORKING), task manifest 2026-10-01, runtime-код,
API списка/confirm редакций и связанные тесты. M1 `1.4` остаётся FROZEN,
CURRENT=NO. Методология, схема БД, права и опубликованные артефакты не меняются.

После confirm frontend повторно читает серверный список редакций. Более новая
редакция по `id`, а при отсутствии сравнимых id — по времени, имеет приоритет.
Поколение запроса защищает от обратного порядка ответов в одной вкладке. Подписи
форм определяют, какие draft-ключи допустимо очистить.

## Проверки и готовность

Локальный минимум выполнен: адресная frontend-регрессия — 1 PASS; полный
frontend-набор — 67 PASS; два адресных browser-сценария — 2 PASS; `npm run lint:js`
— PASS; `npm run build:web` — PASS; `git diff --check` — PASS. Перед слиянием
обязательны зелёные CI jobs `frontend` и `pytest` актуального head.

## Риски и откат

Confirm выполняет дополнительный защищённый GET; при его недоступности используется
локальный порядок без отмены уже успешного подтверждения. Миграции и конфиг не
нужны. Откат — revert PR.
