# Рецепт предметного артефакта

Применяется к методологии, ролям, контекстам, кейсам, сценариям, prompts и политикам.
Предметный смысл хранится вне исходного кода; алгоритмы загрузки и проверки — в коде.
См. [инвентарь пакетов](../../assessment_definitions/README.md) и
[runtime-контракт](../architecture/assessment-runtime.md).

## Выбор существующего контура

Все пути ниже относительно `assessment_definitions/`. Это существующие примеры,
не требование приводить разные manifests к выдуманной общей схеме.
Версии всех этапов M могут пересматриваться. Таблица показывает наличие файлов
и средств проверки, не окончательную применимость или методологическое утверждение.
M6–M8 пока не внесены как задачи проекта; готовых контуров этих этапов здесь не заявлено.

| Вид | Существующий пакет / контракт | Проверка из корня репозитория |
| --- | --- | --- |
| Методология 1.1 (M2) | `methodologies/competencies_4k/1.1`, schema v2, import-profile и normative-control | `.venv/bin/python -m pytest tests/unit/test_methodology_1_1_package.py` |
| Базовые роли M3 | `role_profiles/competencies_4k/1.1`, base_roles и role_profile_contract | `.venv/bin/python -m pytest tests/unit/test_m3_base_roles.py` |

| Кейсы M5 | `cases/competencies_4k/1.1`, case-package и JSON Schema | `.venv/bin/python scripts/build_m5_case_package.py --verify-only`; `.venv/bin/python -m pytest tests/unit/test_m5_case_package.py` |

Команды проверяют существующие пути и контракты, не любой новый каталог автоматически.
Для новой версии добавить её в проверки и загрузчик; показать, что тесты читают именно
новый пакет. У M2/M3/M4 нет общего `--verify-only`; исходные документы и команды сборки
описаны в README пакетов. Импорт в БД не заменяет файловую валидацию:
`scripts/import_methodology_bundle.py` даже без `--apply` подключается к БД.
Не запускать его как безопасную офлайн-проверку.

M3/M4 ещё содержат предметные настройки в сборщиках — [ART-02/03](artifact-debt-register.md).
Проверка текущего кода не подтверждает независимость нормативного эталона.

## Порядок создания или переноса

1. Зафиксировать источник/версию/раздел, владельца содержания, PM/LU и потребителей.
   Нет обязательной нормы — остановить зависимую работу, не дописывать её в prompt.
   Различить статус источника, статус интеграционного пакета, наличие задачи и
   фактическую готовность runtime. При корректировке M выполнить анализ влияния
   на пакеты, контракты, тесты и snapshots; не распространять новые нормы на старые результаты.
2. Выбрать существующий тип и формат пакета, целевой путь и правила версии.
   Нет подходящего контура — сначала записать задачу/раздел проектирования расширения:
   контракт, загрузчик, валидация, публикация, snapshot и совместимость. Получить
   решение технического владельца и владельца смысла до зависимой реализации.
   Отдельный PR нужен для самостоятельного результата; не создавать универсальную
   инфраструктуру заранее и не вводить ad-hoc формат молча.
3. Для изменения опубликованного содержания создать новый draft. Сохранить
   идентификатор, версию, статус, происхождение, владельца и checksum по формату
   данного контура. Если формат не имеет поля владельца, указать его в задаче/Registry;
   не добавлять неподдерживаемое поле без изменения контракта.
4. Сохранить содержание отдельно от Python/JS. Генератор не должен воспроизводить
   предметный текст из встроенного словаря. Перенос без изменения смысла проверить
   по независимому эталону, а смысловые исправления выделить отдельно.
5. Проверить структуру, ссылки, полноту и контрольные суммы. Для файлов SHA-256
   считается по исходным байтам, без скрытого trim/переформатирования. Для JSON-снимка
   использовать канонизацию действующего контракта, а не произвольный json.dumps.
6. Проверить потребителей, отсутствие скрытого fallback и исполнение старого снимка
   после изменения текущего пакета. Обновить traceability и реестр долга.
7. Публиковать через действующий lifecycle и полномочия; snapshot фиксирует точное
   содержимое/версии/checksum. Файловый draft не становится автоматически официальной
   конфигурацией или новой нормой. Технический PASS не равен методологической приёмке.

## Минимальный существующий пример: prompt лаборатории M5

```text
assessment_definitions/prompts/m5_generation_lab/v1/
  prompt.md
  manifest.json
```

Manifest имеет `schema_version`, `id`, `version`, `status`, `scope`, `owner`, `source`
и `artifacts` с `name`/`sha256`. Полный рабочий пример —
[manifest.json](../../assessment_definitions/prompts/m5_generation_lab/v1/manifest.json).
Контракт этого примера допускает только `draft` / `laboratory_only`, это не формат
публикации официального оценочного агента. Владелец указан ролью; назначение
конкретного человека остаётся открытым и не должно выдаваться за завершённую приёмку.

Для независимого сравнения SHA-256 файла с manifest:

```bash
shasum -a 256 assessment_definitions/prompts/m5_generation_lab/v1/prompt.md
.venv/bin/python -m pytest tests/unit/test_m5_generation_lab.py
```

Первую строку сравнить с `artifacts[0].sha256`; вторая проверяет загрузчик и регрессии.
Совпадение хеша показывает целостность, а не правильность предметного смысла.
Исторический prompt намеренно без финального перевода строки; автоформатирование
изменит checksum. Новая версия должна получить собственный каталог и manifest.

Этот loader перед новым запуском читает пакет, проверяет его и сохраняет
`prompt.text/version/checksum/artifact`. Исполнение `generate` читает только snapshot.
Изменение prompt требует нового артефакта; переключение выбранной версии сейчас
выполняется ссылкой `PROMPT_PACKAGE` в составе релиза. Универсальный механизм выбора
всех версий или общий CLI-валидатор этим рецептом не вводится.

## Граница выпуска и откат

Опубликованные пакеты и сохранённые snapshots не переписывать. Согласовать,
как новые запуски возвращаются на предыдущую совместимую конфигурацию и как
завершаются начатые сессии. Если нужна миграция, сначала план совместимости,
восстановления и допуск владельца; feature flag не делает миграцию обратимой.
Точные команды и ограничения для каждого переноса сохранять в файле задачи.
