# Проверка генерации M5 на test

Целевой стенд: `https://test.4k-assistant.ru`. Кандидат версии: `2.1.27`.
Статус развёртывания фиксируется отдельно: наличие этого документа или версии
в локальном коде не означает, что кандидат уже появился на стенде.

## Что проверяет лаборатория

Лаборатория формирует начальное предъявление явно выбранного Case для двух
BaseRole текущего WORKING-пула. Вход — синтетическая ролевая проекция из
ветви M5 и названия M3. Это не профиль реального участника и не опубликованный
PersonalizedProfile M4. Реальный M4, исполнение Dialogue, оценивание M6 и
подбор/последовательность M7 подключаются отдельными этапами.

Два режима различаются явно:

- `template`: сборка предъявления и позиции роли из сохранённых материалов,
  без LLM; подходит для воспроизводимой технической проверки.
- `llm`: реальный вызов настроенного DeepSeek для переформулировки начального
  предъявления с учётом роли. Скрытые факты и IndicatorID в этот запрос не
  передаются. Ошибка провайдера не заменяется шаблонным ответом.

Успешная генерация означает только получение структурного результата.
`methodological_qa=NOT_RUN`, `admitted_for_assessment=false` сохраняются всегда.
Проверку смысла, мандата, отсутствия подсказок и сохранности инварианта выполняет
методолог. 14 неразрешённых целей K2 остаются открытыми.

## Ручная приёмка

1. Проверить `/users/version` на стенде; записать commit CI-деплоя и версию.
2. Войти суперадмином, открыть **Админка → Prompt Lab → M5 · Проверка генерации
   по ролям**. У обычного участника API лаборатории должен быть недоступен.
3. Выбрать `SCR.A01`, роль «Руководитель команды» и сборку без LLM. Нажать
   «Сформировать кейс». Сохранить отображённый ID прогона.
4. Повторить для «Менеджера проекта, продукта или процесса». Сравнить объект
   ответственности и полномочия: у проектного менеджера не должна появиться
   административная власть над чужими сотрудниками.
5. В обоих результатах раскрыть «Сохранённые входные данные, результат и
   проверки»: проверить роль, версию/контрольную сумму Case, две отдельные
   цели Observability, `input_integrity=true`, `output_integrity=true`.
6. Перезагрузить страницу и открыть первый прогон по ID. Предъявление и снимок
   должны совпасть с первоначально показанными.
7. При настроенном провайдере повторить две роли в режиме LLM. Записать реальные
   ID и содержательный verdict отдельно от технического статуса `completed`.
   При недоступном LLM этот пункт остаётся NOT_RUN с указанием причины.
8. Для автоматического прохода выбрать роль и нажать «Пройти 20 кейсов выбранной
   роли», затем повторить для второй роли. Каждый Case получает отдельный ID
   и запись; интерфейс показывает счётчик завершённых/неуспешных результатов.
   Пакет запускается последовательно браузером, поэтому вкладку нужно оставить
   открытой до конца. Это не фоновая очередь и не селектор M7.

## HTTP и повтор запроса

- `GET /users/admin/m5-lab` — каталог Case/ролей и доступность LLM.
- `POST /users/admin/m5-lab/runs` — запуск с `run_id` UUID, `case_id`,
  `base_role`, `mode` (`template` или `llm`).
- `GET /users/admin/m5-lab/runs/{run_id}` — чтение сохранённого артефакта.

Все операции требуют существующей сессии суперадмина. Автоматический клиент
может вызвать тот же API для матрицы из 20 Case × 2 роли; аутентификация не
обходится. Токены не помещаются в примеры, логи или экспорт.

Повтор POST с тем же `run_id` и тем же запросом возвращает имеющуюся запись,
не делая повторного LLM-вызова. Изменение запроса с прежним ID даёт 409.
Для нового прогона нужен новый UUID. После обрыва связи сначала прочитать
существующий прогон. При остановке API-процесса запись может остаться `running`;
этот первый вариант лаборатории не возобновляет генерацию автоматически.

## Артефакты PostgreSQL

Таблица `m5_generation_lab_runs` создаётся совместимым добавлением при старте
приложения; старые assessment-таблицы и результаты не изменяются. Поля:

- `run_id`, `created_by`, `created_at`, `completed_at`, `status`, `error_code`;
- `request_checksum` — контроль повторных запросов;
- `input_json`, `input_checksum` — Case, синтетический профиль, сценарий,
  проектная Observability, версия/текст/checksum инструкции;
- `output_json`, `output_checksum` — предъявление, режим, длительность,
  сохранённые цели и технические/методические статусы.

Снимок защищён от UPDATE; завершённый результат также неизменяем.
Для проверки конкретного созданного прогона администратор может выполнить
параметризованный read-only запрос:

```sql
SELECT run_id, status, input_checksum, output_checksum,
       input_json->'profile' AS profile,
       output_json->>'presentation' AS presentation,
       output_json->'observability' AS observability,
       output_json->'checks' AS checks
FROM m5_generation_lab_runs
WHERE run_id = :run_id;
```

Просматривать следует только собственные синтетические QA-прогоны по известным
ID. Пользовательские и production/test персональные данные для этого не нужны.
Записи сохраняются после проверки; удаление не является частью прогона.

## Проверки перед выпуском и откат

Обязательны lint, frontend build, unit, HTTP и интеграционные тесты на отдельной
БД с `test`/`pytest` в имени, затем review diff. Сборка проходит через PR и CI;
штатный deploy после merge в `main` публикует её на test. В отчёте приёмки
фиксируются ссылка PR, commit, версия, URL и ID двух реальных ролевых прогонов.

Откат — вернуть предыдущий commit приложения штатным процессом. Новая таблица
с артефактами остаётся для аудита; существующие assessment-сессии от неё не
зависят. Новых переменных окружения нет; режим LLM использует действующие
настройки провайдера.
