2. ОБЛАСТЬ И НЕИЗМЕННЫЕ ПРАВИЛА

Включены UI, реальные entry/handlers, API, источники/записи и фоновые операции, необходимые ровно этому пути. Использовать существующие контуры/сущности/права, исправлять связанные legacy-потребители там, где они реально мешают шагу.
Не ограничивать исправление одной подписью UI, если причина в API/данных/оркестрации.

ProgramDefinition — точная версионируемая связка конфигурации, каталога, source refs и допустимых опубликованных версий ролей. Подключение организации, назначение человеку, профиль и индивидуальный маршрут различны.
Опубликованный комплект не наполнять сведениями компании/участника и не переписывать его ради исправления анкеты. Использовать согласованную published-программу; необходимые точные зависимости проверять явно.
«Специалист / эксперт» — роль оценки; должность/профессиональная область и роль доступа аккаунта имеют свои назначения. Отдельное ручное согласование RoleProfile при каждом назначении не вводится. Девять кейсов — состав доступного каталога; выбор роли не закрепляет человека за девятью фиксированными ситуациями и не требует предъявить все девять в этом прогоне. Состав подготовки определяется действующей программой/M7; приёмка заканчивается на первом предъявленном кейсе.
Сохранять выбранные M1–M8 в применимой части, действующие источники и admission. Расчёты/Results после первого старта этим заданием не реализуются и не принимаются. ФИО/контакты не передавать в содержательную генерацию кейсов или оценивание.

До первого подбора Case фиксируется PersonalizedProfile. До старта должны быть подготовлены зафиксированный профиль, допустимые план/маршрут и эффективные параметры времени; их наличие само не запускает календарное окно.

Дальнейшее решение кейса, оценивание, итоговые баллы, отчёт, пауза/возврат и завершение Cycle не входят.

Полный purge/перенос, история отмен всех поколений, cancel/accept-revoke concurrency, общий редизайн и весь OTHER-backlog этой задачей не запускаются. Их прежние обязательства сохраняются. Реальный LLM выполняется в выбранной конфигурации с конечными действующими token/time/retry/repair-пределами. На каждый диагностический полный запуск — одно новое прохождение до первого кейса; подготовка может требовать нескольких AS и нескольких вызовов по программе.

Сначала воспроизвести текущий путь: суперадмин создаёт новую организацию, подключает точную published-программу «Пилот 4К · 9 кейсов» из раздела 1, затем добавляет администратора.
Доказать настоящий submit → handler → PUT → сохранение → точный GET → отображение и reload. Имя в списке не доказывает connection.
Подключение не требует заранее подтверждённой анкеты новой организации. Дополнительная загрузка анкет не удерживает успешную команду подключения в бесконечном выполнении.
Проверить потерю ответа, null/чужой/вытесненный readback, slow/error и повтор: успех только для подтверждённого точного исхода; неизвестный исход обозначен неизвестным с безопасной проверкой.
Исправления export/readback R10 уже были внесены. Если путь работает — предъявить доказательство, не переделывать его.
Вход созданного администратора должен давать только предусмотренную область своей организации; ordinary admin не получает право подключения программы.

Точки анализа: web/js/wiring.js, web/js/entries/admin-organizations.js, web/js/screens/admin/organizations.js, Api/assessment_programs.py, соответствующие routes/доступы.

PS-02. Администратор: сведения организации и достоверная готовность
Связь: PG-R2; относящиеся к пути ST-R1, ST-R2; R02.
Администратор заполняет полную синтетическую анкету точного scope, видит preview и подтверждает именно просмотренную редакцию. «Автор сведений» обозначает происхождение организационной информации.
После успешного подтверждения/readback/reload видна фактическая confirmed revision. Изменённая/чужая/устаревшая revision не подтверждается как актуальная.
Устранить подтверждённый остаток PG-R2: пока GET выполняется или завершился ошибкой, отсутствие revision в локальном массиве не означает «анкета не подтверждена». Loading/unknown/error/реальный missing/confirmed различаются.
Не предлагать переподтвердить уже сохранённое только из-за ошибки чтения. Поздний ответ прежней организации/оценки не заменяет новый scope.
Устранить относящееся к пути ложное busy ST-R1 при локальном просмотре/отказе от действия. Открытая карточка сама не является выполняющейся серверной mutation.
В текущем назначении должны быть доступны достаточные идентичность/роль/программа/этап и известные факты. Полную историю отмен всех поколений этой подзадачей не добавлять.

Точки анализа: organizations.js questionnaireLoadStates/assignmentReadinessMarkup/trackOperation, wiring preview/confirm, Api/questionnaire_sources.py и routes.

PS-03. Администратор: участник, роль и точное назначение
Связь: PG-R1/PG-R3; ST-R3; сделанные R01/R02.
Штатно добавить участника с обязательными сведениями, включая должность. В UI «Роль в оценке»; все шесть BaseRoles берутся из применимого каталога, для пилота доступен specialist_expert («Специалист / эксперт»), остальные видны как недоступные по согласованному правилу.
HR/Sales/должность не вводятся как новые BaseRoles. Роль доступа admin/member не подменяет роль оценки.
Назначение создаёт один точный assignment и source bindings с подходящими программой/конфигурацией/каталогом/ролью/редакцией анкеты. Транзакция атомарна; отказ не оставляет половину связки.
Повтор/двойной клик/потеря ответа не создают дубль и не стартуют Cycle. Сначала устанавливается исход уже отправленной операции.
Недоступная роль, чужой scope, неподключённая программа и mismatch дают точную причину и предусмотренное действие.
Проверить ST-R3 на реальной PostgreSQL: два назначения одной конфигурации с различными применимыми источниками/профилями и более поздним чужим job. Текущая строка и участнический путь не должны получать чужую подготовку по одному latest user/org/config.
Сначала установить достижимость и правильные связи существующей модели, затем исправить найденное. Уже существующую точную Cycle.assignment_id привязку не проектировать заново. Если переиспользование profile допустимо и однозначно, не создавать второй профиль только ради теста.
Для неоднозначного legacy — честная невозможность уточнить состояние, без опасного действия по догадке.

Точки анализа: Api/routes.py _build_admin_organizations, assessment_assignment_sources.py, assessment_programs.py, assignment/readiness endpoint, organizations.js.

PS-04. Участник: знакомство и автоматическая подготовка
Связь: PG-R1/PG-R3; ST-R3/ST-R4; относящиеся к входу ST-R5; сделанные R03/R04.
Участник входит своей сессией и видит нужные организацию/назначение/роль/условия. Личность/права не берутся из URL.
Обязательное знакомство выполняется настоящими операциями, ответы и подтверждение сохраняются после refresh/повторного входа. Подтверждённое не запрашивается заново без предметного основания.
Устранить PG-R1: отсутствие должности/других данных участника, отсутствие назначения, readiness/binding mismatch и сведения организации имеют разные безопасные причины и действие ответственного.
После подтверждения обязательного знакомства система автоматически выполняет resolve-profile и штатную participant-owned подготовку. Обязательного ручного оператора между знакомством и стартом нет; такой auto-trigger уже был в коде, его не создавать заново.
PersonalizedProfile фиксируется до первого использования для подбора/формирования Case, с восстановимым происхождением; программа, роль, контекст и revision не теряются.
Реальная подготовка проходит штатный LLM/validation/admission и формирует допустимый план/маршрут/AS. Completed job сам по себе не означает разрешённый старт. Подтверждаются фактические deepseek/deepseek-flash вызовы в рамках этой preparation operation, generation operation refs, final tester/challenger, при применённом штатном repair — конечный кандидат и повторные проверки, admitted_for_participant=true, сохранение и предъявление именно принятой AS. Provider probe отдельно не подтверждает этот путь.
Допустимы PASS и PASS_WITH_WARNINGS только по действующему продуктовому admission и при выполненных обязательных проверках. INCOMPLETE/FAIL/REVIEW_REQUIRED или admitted_for_participant=false не разрешают старт. Candidate, compiled Case, snapshot и participant payload сверяются каждый по своему контракту и связи; разные типы объектов не обязаны иметь один checksum.

Включить PREP-DIAG-01 в диагностику и исправления PS-04. Исторический факт: на 4bab7230d8fa484fb8d922ee7d8b49b63674268d операция c570a030-a47a-4eed-81f9-37c92e1441d8 для CASE.SPEC.02 v0.6 остановилась с M5_FUNCTIONAL_AS_NOT_ADMITTED:INCOMPLETE, AS не выдана, старт не выполнен, ответов 0. Точные check IDs и первопричина исторического INCOMPLETE — UNKNOWN. Синтетическая регрессия экспортёра и исправленные ошибки runner их не восстанавливают и причинность не доказывают.
Сначала использовать сохранённые первичные evidence и код; если их недостаточно, выполнить обоснованную диагностику/реальный прогон на целевом комплекте. Новому run дать собственную идентичность, не выдавать его причину за доказанную причину старого run. Сохранить IDs обязательных checks, статусы/безопасные причины, protocol errors, candidate/operation refs и результат terminal-export до cleanup.
Установить, что препятствует допуску: технический сбой/неполный протокол, дефект источника или содержательный отказ проверки. Подтверждённый технический дефект выбранного пути исправить в PATH и повторить проверку. Не объявлять AS некачественной без конкретного check; не добавлять repair для INCOMPLETE и не смягчать admission без отдельного нормативного основания. Если нужно новое предметное решение/утверждённый источник, подготовить точную зависимость с владельцем, продолжая независимую работу.
Queued/running/failed/ready/unknown различимы. Разрешённая read-only проверка подготовки доступна из UI; ST-R4 нельзя закрыть только возвратом action из backend, если renderer его теряет.
Не давать обычному админу/участнику новые служебные права retry/prepare и не превращать административный просмотр в start от имени участника.

Точки анализа: onboarding.js beginPreparation, Api/acquaintance.py, product-cycle-preparation.js, product_cycle_preparation_queue и state/readiness, M4/profile/M7 contracts, organizations.js action mapping.

PS-05. Явный первый старт и общая приёмка
Связь: PG-R3, прежние R03/R09; исходные start/сохранность/права.
До явного действия участника создание/подключение/назначение/просмотр/знакомство/подготовка не запускают календарное окно.
Первый старт разрешён сервером для точного назначения, профиля и допустимого плана. Сохраняются начало соответствующих Cycle/Session, эффективные параметры времени и первое предъявление AS.
Первый кейс реально виден тому же участнику; оценочных ответов 0. Не заканчивать проверку на клике или смене frontend-route.
Повтор команды старта и reload не создают второе прохождение/Session/AS из-за технического повтора.
Закрытие тестового браузера не объявлять паузой/отменой/завершением Cycle.
На окончательном SHA повторить ВЕСЬ процесс от нового суперадмина/организации, а не только последний исправленный экран. Базовый тестовый суперадмин допускается в начальной загрузке; все дальнейшие объекты создаёт сценарий.
Провести независимое чтение evidence по исходным ожиданиям, фиксируя источник → UI/API/данные → проверка → версия → принятие.
После разрешённого выпуска тот же сценарий повторяется в выделенной synthetic-области целевого контура. Main, локальная БД и фактическое развёртывание — разные факты.

6. ОБЩИЕ КРИТЕРИИ ПРИЁМКИ

AC01. Начальная загрузка минимальна. До основного E2E нет заранее созданных организации/connection/admin/member/confirmed questionnaire/assignment/profile/completed acquaintance/start. Точный набор утверждённых начальных источников описан; target/owner marker защищают постоянную и чужие БД от seed/cleanup.

AC02. Тестовый суперадмин штатно создал новую организацию; она читается и сохраняется после reload. Повтор создания обработан по действующему контракту без случайного дубля.

AC03. Использована подтверждённая опубликованная «Пилот 4К · 9 кейсов» с точными program/configuration/catalog/role/source refs, составом каталога и checksum из отдельной публикации. Исходный допуск не подменён диагностическим seed/human_review. Published содержание и использованные snapshots не переписаны; сведения компании/человека в комплект не перенесены.

AC04. Настоящее подключение сохраняет точную связь и подтверждается GET/reload. Отсутствующая анкета новой организации не препятствует самой связи.

AC05. Slow/error/null/foreign readback/потерянный ответ подключения дают достоверный конечный либо unknown исход. Нет ложного успеха/ложного «не подключена» и зависшего выполнения. Проверены реальный entry/dist и безопасный повтор.

AC06. Администратор создан штатно, входит отдельной сессией в свою организацию. Обычный admin не может прямым HTTP подключать программу от имени суперадмина или работать с чужой организацией.

AC07. Полная анкета подтверждена в точном scope и revision. Stale/foreign revision отклоняется. Loading/error GET не превращает сохранённую confirmed-анкету в неподтверждённую; есть достоверная повторная проверка.

AC08. Участник добавлен с обязательными сведениями. Все шесть BaseRoles/доступность пилота получены из применимого источника; доступен specialist_expert. Должность/область деятельности/роль доступа отличимы от роли оценки.

AC09. Штатное назначение атомарно сохраняет один assignment и точные bindings. Повтор/двойной клик/потеря ответа не создают дубль, не стартуют Cycle и не меняют чужие записи.

AC10. Неподключённая программа, недоступная роль, чужой scope, mismatch обязательной анкеты дают точную причину без частичных записей. Серверная проверка не заменена disabled-полем UI.

AC11. Участник входит собственной сессией и видит правильные организацию/назначение/роль. Чужой user/cycle/assignment не открывается подстановкой идентификатора.

AC12. Знакомство и подтверждение сохраняются после refresh/входа. Уже подтверждённые ответы не теряются; отсутствующие данные объясняются конкретно с предусмотренным действием. Нет необъяснённого общего ожидания организации при иной установленной причине.

AC13. Правильный PersonalizedProfile фиксируется до первого подбора Case; его источники/версии восстановимы. Содержательные LLM-входы не содержат ФИО/контактов; цель компании не меняет оцениваемый конструкт.

AC14. Автоподготовка после обязательного знакомства работает без обязательного ручного оператора. Есть реальные provider traces той же операции, штатные validation/admission конечного кандидата, план/маршрут/AS; PASS_WITH_WARNINGS допустим по действующему контракту, INCOMPLETE не превращается в PASS. PREP-DIAG-01 рассмотрен адресно: конкретная новая диагностика/исправление/повтор либо доказанная зависимость; историческая причина UNKNOWN не выдумана. Очереди/ошибки/готовность и разрешённое действие проверки подготовки видны честно. Локальная карточка/отказ не оставляют ложного busy.

AC15. PostgreSQL-проверка разных назначений одной конфигурации, профилей/revision и чужого более позднего job не показывает присвоения чужой подготовки. Если для legacy точность не подтверждена, UI не угадывает. Область технических fixtures описана отдельно от основного E2E.

AC16. До явного start соответствующий серверный старт/календарное окно не зафиксированы. Completed preparation без действительного start gate не выдаётся за готовность. Параметры обоих времён и их источники подготовлены по M7.

AC17. Явный первый start сохраняет правильные Cycle/Session и время, первый кейс реально предъявлен, оценочных ответов 0. Повтор/reload не создают лишних объектов и не сбрасывают исходный старт.

AC18. Собран единый итог на окончательном SHA: исходная диагностика, исправления, целый повтор на новых owned-данных, browser/entry/API/PostgreSQL/real-provider evidence. Независимый проверяющий может восстановить путь; код/main/deploy/приёмка и NOT_RUN отделены. На 1440 и узких 320/390/768 проверены доступность существенных действий, длинные данные и пояснения затронутых экранов; повторять полный real LLM на каждой ширине не требуется.

По каждому AC — PASS/FAIL/NOT_RUN/BLOCKED, SHA, конкретные данные/способ/подмены, evidence и оставшийся подпункт/причина. Код, локальные проверки, реальный provider, main, CI, deploy и приёмка имеют отдельные фактические результаты. PASS узкой функции не закрывает весь критерий или процесс; недостающий подпункт нельзя скрывать общим PASS. NOT_RUN не превращается автоматически в новый дефект.

7. КАК ВЫПОЛНЯТЬ И ВЫЯСНЯТЬ ПРИЧИНЫ РАЗРЫВА

Шаг 1. Зафиксировать PATH 1.3, выпуск настройки через PR #167 / 7221671 / 2.0.62 и актуальные main/среду; обновить устаревшую текущую передачу. Использовать готовые профиль/runner из main. Завершить ранее разрешённую отдельную публикацию целевой программы либо получить уже состоявшийся результат; зафиксировать точные источники/receipt, прежние исправления и пробелы. Проверить target/ownership без повторения отдельного расследования БД.
Шаг 2. Проверить, был ли диагностический прогон, пригодный для целевой программы и точно идентифицированного SHA. Однокейсовый диагностический run и no-LLM регрессии настройки сохраняют свою ограниченную область; весь PATH ими не закрывается. Если был — сохранить его как исходное доказательство с областью применимости; не повторять автоматически уже доказанное и не требовать ещё одного платного запуска только из-за нового имени задания. Если прогон отсутствует/неполон/относится к другому коду или обходит существенные шаги готовыми данными — на готовом контуре выполнить недостающую исходную диагностику ДО соответствующих исправлений продукта. Сохранить первый разрыв; непройденные зависимые шаги отметить явно. Результаты после изменения кода не выдавать за состояние до исправления.
Шаг 3. Для каждого расхождения сопоставить исходное требование, план исполнителя, код, тестовое ожидание, отчёт, попадание в main и развёртывание. Не назначать единую причину всем ошибкам заранее.
Шаг 4. Выполнять PS-01…PS-05 в согласованной области: зарегистрировать первый разрыв, установить причину, исправить, повторить и продолжить путь. Не ждать полного прохождения при блокирующей ошибке и не ограничиваться выдачей нового списка багов владельцу. Независимые части можно готовить параллельно; доказательная цепочка остаётся одной. Сделанное не переделывать, остаток исправлять.
Шаг 5. После адресного исправления повторять нужные проверки, а на окончательном кандидате — весь путь и применимый полный набор EVC. Один ответ/commit/карточка не означает отдельный выпуск.
Шаг 6. Передать код, общее покрытие, evidence и причинный разбор. После разрешённого выпуска выполнить целевой synthetic readback/прогон и отдельно подтвердить приёмку развёрнутого результата.

Для дефекта достаточно записи:
ID → ожидали → получили → первый потерянный переход → причина/доказательство либо «не установлена» → исправление/commit → повтор → остаток.
Категории причин: неполное/противоречивое требование; пропуск реализации; неверный тест; скрытая подмена; данные/артефакты; UI/API-интеграция; старый/невыпущенный код; ограничение среды; ошибочное закрытие. Допускается несколько причин.

Общая запись состояния по EVC: завершено / активный шаг / следующий шаг / блокер. Не требовать от владельца ручного участия после каждого технического шага.
Новые продуктовые/методологические развилки и необратимые изменения вне области выносить адресно; независимую работу продолжать.

9. ПРОВЕРКИ, ВЫПУСК, РИСКИ И ОТКАТ

Проверки: применимый минимум EVC для затронутого поведения; frontend regression, lint/build/dist при затронутом frontend; backend/unit/HTTP; реальная isolated PostgreSQL для транзакций/сохранности/повторов/lineage; настоящий browser; разрешённый real-provider прогон. Точные команды брать из актуального package/tests README. Итоговый набор относится к окончательному SHA, CI — к его актуальному head.
Проверки извлечённой функции/regex дополняют настоящий путь, не заменяют его.
Учесть историческую коррекцию аудита: fetchWithDeadline уже существовал. Не вводить новые таймауты по ошибочному утверждению «таймаута нет»; исправлять установленную причину состояния.

Сохранять публичные контракты и историю. Если необходима схема/миграция, обосновать её в затронутой подзадаче, обеспечить совместимость и восстановление по правилам репозитория; не расширять модель заранее.
Published артефакты не переименовывать/перезаписывать in-place. Нужда в новой нормативной публикации — отдельная зависимость владельца, не скрытый fallback.

Флаги передачи:
branch_push=true после локальных проверок;
pr=true для согласованного независимо принимаемого результата;
merge=false до отдельного решения выпуска;
deploy=false до отдельного решения выпуска;
version_bump=false до согласованной подготовки окончательного release candidate;
artifact_publish=false для PATH; отдельное ранее выданное разрешение на восстановление/публикацию утверждённой «Пилот 4К · 9 кейсов» сохраняет свой узкий объём, а его receipt используется как вход PATH. Оно не разрешает новые нормативные публикации или подмену source QA. Загрузка точных утверждённых release-источников в owned-БД для теста не меняет постоянную публикацию.
Флаги не означают запрета готовить весь результат/тесты. Они сохраняют отдельный управляемый выпуск. Ready preflight/CI выполняются по действующим правилам после допуска соответствующего кандидата.
CI/deploy настройки через PR #167 уже состоялись; эти факты не означают разрешения на merge/deploy новых продуктовых исправлений PATH. Прежние флаги выше сохранены. Выполненные checks #167 относятся к выпущенному инструменту; изменения PATH проверяются на своём окончательном SHA.
Если для PATH потребовались новые изменения кода, до их разрешённого deploy проверка общего стенда с этими исправлениями остаётся NOT_RUN; локальный PASS и merge её не закрывают. Если весь путь подтверждён на уже выпущенном коде без новых изменений, использовать его точный SHA и фактический серверный прогон; пустой PR, искусственный version bump и повторный deploy ради отчёта не нужны. Приёмка развёрнутого пути подтверждается отдельным фактом прохождения.

Откат: ограниченный revert кода/кандидата, отключение новых операций при необходимости, сохранение уже созданных bindings/profiles/исторических snapshots. Синтетическая среда удаляется отдельно после evidence; откат UI не меняет историю назначения и не запускает/останавливает Cycle сам.
