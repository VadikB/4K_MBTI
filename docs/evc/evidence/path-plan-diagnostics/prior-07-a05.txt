ARCH-A05 — ПОКРЫТИЕ, ОБЕЩАНИЕ ПРОДУКТА И ПИЛОТНЫЙ БЮДЖЕТ
Владельцы: продуктолог + методолог; реализация — planning/results/UI.

Повторно проверено на main 2.0.16:
Нормативные матрицы SourceSet: K1 17, K2 14, K3 12, K4 18 = 61 IndicatorID.
CASE.SPEC.01–09: 55 вхождений целей, 39 уникальных, 22 отсутствуют.
Отсутствующие:

Состав каталога и нормативных матриц после исходного аудита не изменился.

Исторический расчёт «24 уникальные цели за 60 минут» подтверждается только моделью отбора по верхней planned duration. При нижней границе получается 30. Это не эмпирическая скорость участника. Аналогично расчёты под другие бюджеты являются аналитикой, не правилом генерации или гарантией достаточности. Сумма planned ranges всех девяти 122–155 минут не блокирует пилот и не является целевой суммой.

Принятое решение PILOT-120:
1. Участник имеет 7200 секунд учитываемого прохождения на весь Cycle, окно 259200 секунд. Не выделять ещё 120 минут на каждую Session.
2. Подбор определяется целями и контекстом. Общая плановая длительность не ограничена этим бюджетом; Case/AS не урезаются ради него. Это не требование бесконечной генерации или обязательного прохождения всех девяти Case.
3. При исчерпании фактического бюджета сбор закрывается по действующим правилам, материал обрабатывается до результата с ограничениями. Таймер не продлевается до плановой суммы.
4. Принятие этого допущения не уменьшает M2 denominator и не объявляет частичное покрытие полным.

Необходимое разделение в данных/отчёте:
— каталог: проектная возможность 39/61;
— конкретный план Cycle: выбранный состав целей, без притворного сведения 61 к доступному каталогу;
— фактическая траектория: предъявленные материалы, открытые ветви и возникшие возможности;
— Evidence/EB: полученные и допустимые основания;
— IA/admission: допустимые вклады и причины отсутствия;
— Result: достаточность по действующим M6–M8, частичный/полный результат отдельно.
Существующая формула partial_score по допустимым вкладам не отменяется и не заменяет знаменатель нормативного покрытия; оба смысла показываются отдельно. Нет требования назначить низкий уровень по отсутствующим 22 индикаторам.

Задание A05.1 — честное покрытие:
Входы: scope.json/m2-sources.json, frozen target sets, фактические C45/Evidence/IA, rules M6–M8.
Выход: воспроизводимая coverage matrix с указанными уровнями, пользовательская формулировка ограничений, варианты развития каталога из 02_Task_Order_and_Decisions.txt.
Приёмка: ни одна метрика plan/catalog не выдаётся за фактическую оценку; потерянная возможность, отсутствие данных, L0 и техническая ошибка различимы; полный состав M2 сохраняется. Уровень полноты не повышается простым изменением UI/denominator.

Задание A05.2 — проверить PILOT-120 на фактическом стенде:
Входы: scripts/configure_sales_pilot_timing.py, M7 parameter resolution, утверждённая тестовая организация/конфигурация, API/UI.
Main содержит VALUES=7200/259200 и приоритет program revision; без revision остаётся 3600. Сохранённый real-provider SPEC09 run имеет 3600. Наличие кода не подтверждает публикацию настройки для целевого пилота.
Работа: прочитать текущую revision, применить принятое значение штатным versioned механизмом в разрешённой области, сохранить readback и snapshot нового Cycle. Если настройка уже есть — ничего не перепубликовывать.
Приёмка:
— backend snapshot, UI и report согласованы: 7200, program source, правильные org/config/revision/checksum;
— новый Cycle с любой плановой суммой, в том числе больше бюджета, не получает отказ из-за суммы; несколько тестовых значений нужны только для проверки общего свойства;
— выбор следующей полноценной AS не отбрасывается потому, что её planned duration больше остатка; фактическое отсутствие времени обрабатывается корректно;
— генератор/tester не получают требования сжать содержание до бюджета;
— граница 7199/7200/7201 секунд, pause/resume, provider wait и смена Session сохраняют правильный учёт; late Turn отклоняется;
— истечение времени внутри AS сохраняет уже полученный материал и проходит до M8; непредъявленное не превращается в Evidence;
— изменение program revision не меняет начатый Cycle; 72-часовое окно проверяется отдельно;
— отсутствие нужной program revision видно как несовпадение конфигурации, а не объявляется успешным 120-минутным пилотом.

Решение о расширении каталога, изменении обещания, состава/числа Sessions или будущего бюджета — продуктолог/методолог. Для текущего пилота повторного выбора 120 минут и согласования произвольной плановой суммы не требуется.
